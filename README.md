## 發碼前的檢查清單

**這幾件事全部做完之前，一組碼都不要發、網址也不要給幹部。**

它們寫成一張清單而不是散在正文裡，是因為它們有一個共同的**截止點**：
**「資料庫裡開始有別人的私人資料」的那一刻。** 發碼是目前最接近它的動作。
分開寫的話，每一項看起來都像「有空再說」。

**但共同的截止點不代表共同的起點，而清單這種東西最會騙人的地方就在這裡。**

下面分成兩組，因為它們是兩種事：一種要等別人回覆，一種你自己按幾個鍵就做完了。
**第一組不能等到最後一天才開始。**

### 要等別人的（現在就送出去）

| | 做什麼 | 誰 | 送出日 | 回覆日 |
|---|---|---|---|---|
| 1 | President / VP 確認活動內容 | 王平（President） | 2026-09-02 | **2026-09-02 ✓** |

**這是清單上唯一有前置時間的一項**（一般要等三天到一週，理由見下面第 1 項）。
它在流程上的位置是**最早**，不是第一：送出去，然後去做別的事，回覆進來再勾掉。

兩格日期不是排版。只填一格的話，「送出去了」跟「回覆了」會分不出來，
而你真正在等的是後面那一格。

> **2026-09-02 這一次兩格是同一天，而那不是因為核准很快。**
> 核准人就是送出的人（王平本人是 President），所以沒有等待，
> 也**沒有真正的外部檢查**——設計活動內容的人跟核准活動內容的人是同一個。
>
> 這一格填掉了，但它這一次沒有發揮它被放進清單的作用。詳見下面第 1 項。

### 自己做得完的（發碼當天，五分鐘）

| | 做什麼 | 完成日 |
|---|---|---|
| 2 | 換一次 Supabase 資料庫密碼 | ______ |
| 3 | 開啟 email 確認（需先接好寄信） | ______ |
| 4 | 作廢開發期間用的 Resend API key，建一把新的 | ______ |

這一組**要留到最後才做**，不是因為麻煩，是因為做完之後開發就變不方便了
（連線字串作廢、每次註冊都要收信）。它們的觸發點是「真的要發碼了」的那一刻，
而上面那一項的觸發點是「現在」。

### 1. President / VP 確認活動內容 —— **外部依賴，現在就送出去**

資料庫裡的活動內容是草案。**沒有確認就發碼，等於讓三十個人開始在還會變動的
題目上寫心得**——之後改題目，那些心得就對不上了。

**它跟下面那一組的差別是前置時間，不是難度。** 那一組是自己按幾個鍵、
五分鐘做完的；這一項要等別人讀完再回覆，可能三天到一週，而那段時間不是你的 ——
催也快不了多少。

清單這種東西會把兩者拉平：並排在同一張表上，看起來就像花的時間差不多。
於是照號碼從上往下做，在最後一天才送出這一項，然後整件事卡住一個禮拜 ——
而且卡住的原因跟技術完全無關。**這就是它被拆出來單獨一組的理由。**

#### 2026-09-02 這一次沒有真正的外部檢查

核准日 2026-09-02，核准人王平（President）——**也就是設計那些活動內容的人。**

這一項存在的用意是「讓一個沒參與設計的人看過再放行」。這一次核准人與
President 是同一人，所以流程上勾掉了，實質上沒有第二雙眼睛。
寫在這裡不是為了留案底，是因為**一格被填掉的清單看起來跟一格被真正執行的
清單一模一樣**，而下一個讀這份文件的人分不出來。

**之後遇到這兩種情況，要找一個沒參與設計的人看過再核准：**

1. 換了 President —— 那時候核准人跟設計者本來就不是同一個人了，
   這一項自然會恢復它原本的作用，別讓它退化成走個形式
2. 活動內容有大改 —— 小修字句不必，改到「幹部要寫的東西變了」的程度就要

**核准的人仍然是 President / VP**——這裡加的不是換人核准，是核准之前多一道
輸入：先請一個沒參與設計那些題目的人讀過，把他覺得看不懂或奇怪的地方帶進核准。
這一項要的是「不熟悉的人讀得懂」，而設計的人恰恰是最看不出這件事的人。

（`activities` 的內容不要刪、只停用，見「不要刪活動」。）

### 2. 換一次 Supabase 資料庫密碼

Settings → Database → Reset database password。換完之後開發期間用過的舊連線字串就作廢。

**為什麼是這個時間點：** 那一刻起資料庫裡開始有只有本人看得到的東西——心得、活動照片，
其中有未成年幹部寫的。在那之前資料庫裡只有測試帳號與公開的活動文案，連線字串外流
能拿到的東西價值接近零。

而那串字的複本比人以為的多：跟 AI 助理的對話紀錄、剪貼簿、終端機歷史，可能還有
你自己沒印象的地方。它是 `postgres` 超級使用者，**繞得過每一條 RLS**——README 前面
那句「就算有人把前端整個拆了重寫，也讀不到別人的心得」，對拿著這串字的人不成立。

`check.sh` 有一條守門擋住連線字串被寫進 repo，但它只管 repo，上面那些地方它管不到。

### 3. 開啟 email 確認

**這一項不是「防假帳號」，是防一個真實的帳號接管路徑。**

2026-09-01 實測：email 確認關著時，註冊端點會**立刻**把帳號標成已驗證、直接回
access_token，一封信都不寄。也就是**任何人都能用別人的 email 註冊，不必證明自己
擁有那個信箱**。

而 Supabase 會把 email 相同的 Google 登入**綁到既有帳號上**（同一天在專案負責人自己
的帳號上實測到這個行為）。兩件事合起來：

> 攻擊者先用「某幹部的 email」註冊、設一組自己知道的密碼。
> 那位幹部之後用 Google 登入同一個信箱時，Google identity 會綁到**攻擊者那個帳號**。
> 幹部升級成 cadre 之後，攻擊者用密碼登入就讀得到他的心得。

只有 email + 密碼那條路需要寄信；Google 那條的 email 已經被 Google 驗過。

> **這一項的前提變過一次，值得記下來（第 11 項的做法）。**
> 2026-08-31 決定把 email 確認延到後面，理由是「假帳號的成本只是資料庫多幾列垃圾，
> 它們什麼都看不到」。那句話當時沒錯，但**不完整**——成本不只是垃圾列，
> 是對一個已知信箱的預先佔位。發現這件事之後，時間點從「有空再說」變成
> **「發碼之前，硬的」**。
>
> 判準跟第 2 項一樣：資料庫裡開始有別人的私人資料的那一刻。

### 4. 作廢開發期間用的 Resend API key

Resend → API Keys → 把開發時建的那把 **Revoke**，建一把新的，換進 Supabase 的
SMTP 設定。

理由跟第 2 項的資料庫密碼一模一樣：那串字在開發期間會出現在對話紀錄、剪貼簿、
終端機歷史裡，複本比人以為的多。

**但它的外洩比資料庫密碼「安靜」。** 資料庫被亂動遲早會被發現；
拿著這把 key 的人可以用 `beyondtaiwannpo.com` 的名義寄信給幹部與家長，
而且 SPF / DKIM 全部會通過 —— 收件人完全看不出那不是我們寄的，
我們自己也不會收到任何通知。

`check.sh` 有一條守門擋住這把 key 被寫進 repo，但它只管 repo。

## 上線後的第一週

前面那些是「東西做好了」。這一段是「讓它真的被用起來」。

**這一段存在的理由很實際：如果你一次把碼發給三十個人，你會在群組裡回答三十次
同樣的問題。** 下面的做法是把那些問題提前講掉，並且讓你在出事時知道什麼時候該踩煞車。

### 有人說「壞掉了」的時候，先拿到資料層的答案

**在處理任何回報之前，先做這件事。**

> **畫面回報不可靠。** 不是因為人不誠實，是因為「我看到什麼」和「系統當下是什麼狀態」
> 是兩件事，而人記得的是前者、還會混進「我以為會看到什麼」。

2026-09-01 實際發生過一次：專案負責人回報「用 Google 登入之後看到『你還不是 BT 幹部』」。
但資料庫顯示他當時是 `cadre`，而那一頁只在角色**不是** cadre 時才會出現——
兩者不可能同時為真。重測時直接對 API 查了一次自己的 `profiles`，回的是 `cadre`，
畫面也正常。結論是回報記錯了，不是 bug。

**重點不是「他記錯了」，是當時有兩個都說得通的假設：**

- 前端的判斷寫錯了（那會打到九月每一個用 Google 登入的幹部）
- 回報記錯了（那什麼都不用改）

**兩者要查的地方完全不同，而選錯的代價是去改一個沒有壞的東西、或漏掉一個會打到
三十個人的 bug。** 所以不要靠判斷去選一邊相信——**設計一個能分辨兩個假設的探針。**

那次的探針是請他在出問題的畫面上，開瀏覽器主控台（F12）貼一段查詢，
直接問資料庫「我現在的角色是什麼」。它把「畫面顯示了哪一頁」與
「系統當下真正的狀態」分開，而那正是兩個假設分歧的地方。

實務上的做法：收到回報時，除了問「你看到什麼」，一併要到**當下的資料層事實**——
是誰的帳號（uid）、角色是什麼、那筆資料在不在。查法見「出事的時候」。
**先有那個答案，再決定要查哪一層。**

### 第一批只發 3 到 5 個人，不要一次發完

先找 3 到 5 個人試跑，理由不是怕程式壞，是怕**你**忙不過來：

- 三十個人同時卡在同一件事，你只能一個一個回
- 三到五個人卡住，你有時間看出那是同一件事，然後把它寫進這份文件

挑人的標準：

- 願意把「怪怪的」講清楚的人，不是會默默放棄的人
- **至少一個在海外**（網路慢的情況只有他們碰得到）
- **至少一個只用手機**（大部分幹部會用手機）

試跑順利再發其餘的人。中間隔一兩天，不要當天就全發。

### 發碼的時候，把這段話一起貼給他

碼單獨丟過去，你就會被問下面每一個問題。**連同這段話一起貼，大部分就不會被問。**

> BT 護照開放了：https://beyondtaiwannpo.com/passport/
>
> 你的邀請碼：`（貼上他的碼）`
>
> 幾件先講：
>
> 1. 點「我有邀請碼，要註冊」，用你常用的 email 註冊，密碼至少 6 個字。
>    **不會寄確認信，註冊完直接就能用。**
> 2. **邀請碼請用複製貼上。** 大小寫和前後空白都沒關係，但打錯字母就進不去。
> 3. 註冊完如果看到「活動資料讀不到」，**重新整理一次就好**，不是壞掉。
> 4. 一組碼只能用一次，而且**只有註冊成功才會用掉**。打錯、重試都不會浪費它。
> 5. 你寫的心得和活動照片**只有你自己看得到**。
>    進度牆上其他人看得到的是你的名字、團隊、大頭照，還有你蓋了哪幾格。
> 6. 有問題寄 beyondtaiwan2020@gmail.com，不要在群組問 —— 群組裡問，
>    你的問題會被洗掉，我也可能漏掉。

第 3 點特別重要：那個畫面是註冊完那一瞬間偶爾會出現的時間誤差，重整就好。
不先講的話，第一個踩到的人會以為自己把它弄壞了，然後不敢再試。

### 每一個問題只回答一次

有人問了你答不出來、或答完發現這其實該寫下來的 —— **回去改這份 README，
然後把那一段貼給他**，不要只在對話框裡打一次。

第二個人一定會問同樣的問題。差別只在那時候你手上有沒有現成的答案可以貼。

**第 3 天**

**第 7 天**

- 再看一次 Actions 的綠勾。這是唯一會讓網站整個消失的東西
- 問一下第一批那幾個人：有沒有什麼「本來想做但不知道怎麼做」的

### 什麼情況要停下來

**立刻停止發碼，先寄信到 beyondtaiwan2020@gmail.com：**

1. **有人說他看得到別人的心得或別人的活動照片。**
   這是唯一一種「先停再說」的狀況 —— 幹部是相信心得只有自己看得到才寫的，
   這件事破一次就再也修不回來。停止發碼，不要自己先去後台翻查證實
2. **第一批 3 到 5 個人裡，超過三分之一註冊不進來。**
   那不是個別打錯字，是有東西壞了
3. **有人的章自己消失了**，而且他確定沒有登錯帳號
4. **網站顯示「資料庫休眠中」，而且照「專案休眠後怎麼恢復」做完仍然沒有恢復**

**下面這些不用停，照文件處理就好：**

- 個別的人邀請碼打錯 → 請他複製貼上
- 個別的人忘記密碼 → 請他自己走登入頁的「忘記密碼？」，見「管理者怎麼處理帳號問題」
- 有人註冊了兩個帳號 → 同上
- 註冊完看到「活動資料讀不到」→ 重整
- 有人覺得某一格題目怪 → 記下來，之後一起改（見「怎麼改活動文案」）

**發碼前的檢查清單沒做完，一組碼都不要發。**

而且是**唯一一項要等別人回覆的**，所以它要最早送出去。

## 這個網站是怎麼來的

> 趕時間辦事的話可以先跳過這一段。
> 但**在你想動任何東西之前**，請回來把它讀完 —— 它解釋的正是「為什麼這裡長這樣」。

### 它解決什麼問題

BT 的幹部一年有 33 件事要做，散在 11 個月裡。原本沒有一個地方看得到
「我做了哪些、還差哪些」，也沒有地方留下當時的想法。這個網站就是那個地方：
一本護照，一格一個章，蓋章時可以寫一句話、放一張照片。

還有一件事同樣重要：**它要讓人願意誠實地寫。** 所以心得和照片是私人的，
只有自己看得到；公開的只有姓名、團隊、大頭照和「蓋了哪幾格」。

### 為什麼是這個架構

**沒有建置步驟。** 整個網站就是 HTML 加幾個 `.js` 檔，GitHub Pages 直接發布。
沒有 npm、沒有打包、沒有 CI 建置。理由很直接：**接手的人不寫程式。**
多一層建置就多一個會壞的地方，而它壞掉的那天，接手的人修不了、也看不懂錯誤訊息。

**資料放 Supabase，安全性做在資料庫裡。** 每個人只能讀寫自己的心得，這件事是由
資料庫的 RLS 規則保證的，**不是由前端的程式碼保證的**。
這個差別很重要：前端的程式碼是公開的，任何人都能改自己瀏覽器裡的那一份；
資料庫的規則改不了。所以就算有人把前端整個拆了重寫，也讀不到別人的心得。

**活動內容放資料庫，不放程式碼。** 課程組要改題目，進後台改一格就生效，
不需要工程師、不需要重新部署。

**三個 js 檔各做一件事**：`passport/src/data.js` 是唯一碰資料庫的地方，
`passport/src/ui.js` 只負責畫畫面，`passport/src/main.js` 只負責接使用者的點擊。
要找「護照的資料怎麼存的」就只看 `data.js`。

2026-08-31（階段 2）之後，護照上面還有一層 `shared/`，那是**整個平台**共用的三個檔案：
`shared/supabase.js`（連線與 client，只有這一份）、`shared/auth.js`（登入、目前使用者）、
`shared/brand.css`（色票與字體，旁邊放 `shared/logo.png`）。
加一個新功能的成本是「開一個資料夾、放一個 HTML、讀那三個檔案」——
**不要再往 `shared/` 塞東西**，理由見 `BT-Site-交接規格.md` §2-3。

### 這些決定是刻意的，不要輕易改

每一條後面都有一句為什麼。**更完整的理由寫在程式碼的註解裡** ——
那些註解不是廢話，是踩過的坑，動之前先讀。

但註解寫的理由必須是真的。**錯的理由比沒有理由更糟**：沒有理由的程式碼會讓人停下來查證，
寫了錯理由的程式碼會讓人相信它然後照著推論下去。2026-08-23 就出過一次——`src/ui.js`
guideCardsHTML 上方有一句註解寫「少一個分類的文案會讓渲染失敗」，但實際上 `esc()`
會把它變成空字串，什麼都不會發生，真正擋住的是 `test/ui-pages.test.mjs` 那條單元測試。
那句錯的話會讓下一個人以為刪掉那條測試也沒關係。所以改程式碼的時候，
連同旁邊那句「為什麼」一起檢查還成不成立。

1. **`entries` 那四條 RLS 規則全部綁本人。**
   這是整個系統唯一真正重要的安全需求：心得和照片裡有未成年幹部寫的東西，
   外洩一次就再也沒有人會誠實寫。前端沒有去要別人的心得只是「不做多餘的事」，
   **真正擋住的是資料庫規則**。

2. **活動內容放資料庫，不要搬回程式碼裡。**
   搬回去的那天起，改一個錯字就得找工程師。

3. **邀請碼的大小寫處理全部在資料庫做，前端一個字都不准改使用者輸入的值。**
   2026-08-17 出過事：前端偷偷把碼轉成大寫，而資料庫是嚴格比對，
   管理員建的小寫碼讓所有人都註冊失敗，畫面卻只說「這個邀請碼不對」。
   病根是「同一件事在兩個地方各做一半」。

4. **連不上資料庫時那個 2 秒的等待，不要調小、也不要改成「全部都重試」。**
   它只針對一種特定錯誤（剛註冊完那一瞬間的時鐘誤差）。
   實測只需要 154 毫秒就夠，但那是運氣好的一次，2 秒是留餘裕。
   改成全部都重試的話，真正的錯誤會被拖成「轉很久然後失敗」，還會被蓋掉看不見。

5. **匯入備份是「先寫進去、再刪掉舊的」，不要改成「先清空再寫」。**
   先清空的話，寫入失敗時使用者的章已經沒了，而畫面還會告訴他「資料沒有被改動」。

6. **「清除這本護照」不會刪掉護照那一列，只會把欄位清空。**
   刪掉的話前端補不回來，那個帳號會變成一本永遠填不了的空護照。

7. **顏色是 Brand Book 七色，字體四種，中文網頁字體只給對外頁。**
   （2026-09-07 改。原本是「三個色碼、不載入中文網頁字體」，Paul 在官網改版時放開，
   詳見 `docs/2026-09-07-官網視覺方向.md` 與下面「官網改版：批 1」那一節。）
   放開的不是紀律而是清單：`check.sh` 還是有白名單，多一個色、多一種字體照樣紅。
   **「海外幹部的網路不一定好、中文字體檔很大」這個理由沒有消失** ——
   所以中文字體只有對外的首頁去載，而且只載 Noto Sans TC 的 900 一個字重；
   登入後每天在用的護照與時間看板一個中文字體都沒載，速度跟改版前一樣。
   `shared/brand.css` 是唯一能決定用哪幾種字體的地方，別處只准寫 `var(--...)`。

8. **每日保活的 workflow 不要停。**
   Supabase 免費方案閒置 7 天會暫停。停掉它，網站會在某個沒人用的兩週後變成空白。

9. **參考資料（`months`／`activities`）的防呆，不准用來遮蔽載入失敗。**
   2026-08-25 出過事：`milestones` 沒被裝進 `S`，而 `(S.milestones || [])` 讓
   里程碑那塊畫面安靜地不渲染，看起來跟「資料庫還沒有資料」一模一樣，
   貼完 SQL 什麼都沒出現，只會以為是 SQL 沒跑成功。判準：防呆是為了
   「這個東西合法地可以不存在」，不是為了「讓錯誤不要吵」。分不清的時候，寧可吵。
   里程碑已於 2026-08-27 從前端移除，這個教訓對 `destinations`／`visas` 一樣成立。

10. **`check.sh` 裡「這個字串必須存在」型的檢查，一律錨定到程式碼的完整形式。**
    這個 repo 的註解會解釋規則本身，於是註解裡的字面會跟真正的宣告重複。
    未錨定的 `grep -q` 被註解餵飽之後會**永遠通過** —— 2026-08-25 就這樣壞過一次：
    一個「讓註解說實話」的 commit 把 `overflow-wrap:anywhere` 寫進註解三次，
    守門從此變成假綠燈，刪掉真正的 CSS 宣告 `check.sh` 照樣全過。
    反過來，「這個字串**不准**存在」型的不受影響：註解污染只會讓它誤報 FAIL，
    那是安全方向。**加新守門時先問自己是哪一型**，然後刪掉它守的那段程式碼跑一次，
    確認真的會 FAIL —— 這件事在 `check.sh` 的檔頭也寫了一份。

11. **有些規則不是壞掉，是它存在的理由消失了。**
    例如 `.slot[data-done="1"] .hint{opacity:.42}` —— 當初是為了讓蓋章後的說明淡化，
    說明退到背面之後這個情境就不存在了，而規則還在會把背面唯一的識別資訊壓掉。

    所以每一條「為什麼這樣做」的紀錄，都該同時寫下它依賴什麼前提。
    前提沒了，規則就該跟著走。

12. **一條測試斷言的是它字面說的那件事，不是它想守的那件事。**
    到 2026-08-26 為止，同一類問題已經發生三次：

    - **同義反覆**（2026-08-25，里程碑）：測試比對「頂欄顯示的數字」與
      「當場再呼叫一次 `milestoneState(S).done`」——兩邊是同一個函式，
      那個函式壞掉的時候兩邊會一起壞，測試照樣全綠。
    - **數錯東西**（2026-08-25，守門）：`grep -c` 數的是**行**不是**次數**，
      同一行裡出現兩次就矇混過關。
    - **取樣太小**（2026-08-26，入境章）：「不同人拿到不同的城市組合」只比兩個人。
      雜湊嚴重偏斜的時候，兩個人**確實**不完全一樣，只是所有人都很像 ——
      實測 3000 個 uuid 只產生 1149 種組合（23 選 10 有 4.1×10¹² 種），
      那條測試從頭到尾是綠的。

    - **守門守錯東西**（2026-08-26，`firstError`）：那條守門想守「milestones 不准
      進 `firstError` 清單」，斷言寫的卻是「`firstError([mo, ac, pa, st, en])`
      這個字面必須出現兩次」。於是依規格把 `destinations`／`visas` 加進清單
      （那兩張**應該**進去）時，它無辜地 FAIL —— FAIL 的理由跟它保護的東西無關。

    上面每一個的形狀不同，病因一樣：斷言寫的是「A 等於 B」，想守的是「A 是對的」。
    （這裡刻意不寫「第幾次」—— 那個數字每加一個例子就會過期，而它不是重點。）

    **寫完一條測試或守門之後，問一次「什麼樣的壞掉會讓它照樣通過？」**
    答得出來就再寫一條，或者把斷言換成守得住那件事的形式。
    然後照第 10 項的做法，真的把它守的東西弄壞一次，確認會 FAIL。

    ### 第二個判準：它通過，是因為被測的東西對，還是因為別的地方也壞了

    上面那個判準問的是「被測的東西壞掉時它會不會照樣過」。這一個問的是相反的方向：

    > **一條測試通過的時候，要能說出它是因為被測的東西是對的才通過，
    > 還是因為系統裡另一個地方也壞著才通過。**
    > 靠另一個 bug 才會通過的測試，會在那個 bug 被修好的當天變紅 ——
    > 而那時候看起來像是「修好一個東西弄壞了測試」，人的第一反應會是去改測試。

    2026-09-02 的實例。看板的驗收裡有一條：「幹部按『確認沒變』會把 `updated_at`
    往前推」。第一次跑**是綠的**。同一份驗收裡另外四條是紅的，其中一條是
    「幹部改不動自己的 `updated_at`」—— 當時那個欄位的授權漏了，前端真的改得動。

    而那條紅的正是那條綠的能綠的原因：測試在比較之前先執行了一次
    `update ... set updated_at = now() - interval '400 days'`，那句**成功了**，
    於是「有沒有變新」當然成立。

    把授權補好之後，那條綠的才變紅，露出它真正的毛病：Postgres 的 `now()` 回的是
    **交易開始時間**，而整個 `do` 區塊是一個交易 —— trigger 寫進去的 `now()` 跟
    函式寫進去的 `now()` 是同一個值，在同一個區塊裡比「有沒有變新」永遠不會變新，
    `pg_sleep` 也不會讓 `now()` 前進。修法是把那一條移到自己的交易裡。

    **這件事最危險的地方在時序。** 如果那四條紅的當天沒有被修，
    這條綠的會一直綠著上線；而它真正的錯誤要等到很久以後、某次不相干的修正之後
    才會浮出來，那時候沒有人記得它跟授權有什麼關係。

    ### 判準：測試在被測的東西壞掉時仍然通過，錯的是它的名字

    這是上面所有例子的共同結論，值得單獨寫一次：

    > **一條測試如果在它被測的東西壞掉時仍然通過，它的名字就是錯的 ——
    > 不是測試不夠嚴，是它測的根本不是那件事。**

    這個判準重要在它指向**不同的修法**。把「不夠嚴」當成診斷，人會去加條件、
    加斷言、把門檻拉高 —— 那不會有幫助，因為問題不在強度，在對象。
    正確的動作只有兩個：**把名字改成它真正測的那件事**，或者**把斷言換掉**，
    讓它真的測名字說的那件事。通常兩個都要做，因為那個名字往往正是你真正想守的東西。

    2026-09-01 的實例：新寫了一條叫「exact match 的規則排在寬鬆規則前面」的測試，
    反向驗證時把順序調反 —— **它照樣通過**。原因是同一次修改裡的另一個條件
    （`!c`）已經讓真實的錯誤形狀不會落進寬鬆那條規則，於是「順序」在真實形狀上
    根本測不出來。那條測試測的是「兩類錯誤分得開」，那也值得守，但它**不是**順序。
    修法是拆成兩條：一條用誠實的名字守「分得開」，另一條用**刻意合成的**形狀
    （現實不會出現、專門用來讓寬鬆規則有機會吃掉它）真的守順序。
    兩層防護各自有測試，拿掉任何一層都會有東西變紅。

    順帶一提，這一條之所以難自己發現：**寫測試的人和寫實作的人是同一個，
    腦子裡「這條在守什麼」是清楚的，所以讀自己的測試名字時會自動補上那個意圖。**
    唯一可靠的檢查是動手弄壞，而且要先確認破壞真的落在被測的那一段（見下面那條）。

    - **移除一個字串，會把所有斷言它不存在的測試變成空的。**（2026-08-26，入境章）
      `MONTH CLEARED` 被換成入境章的時候，有一條測試寫著
      `assert.ok(!book.includes("MONTH CLEARED"))`。它從此**永遠為真** ——
      它「照樣通過」，但通過的理由跟它保護的東西完全無關。
      **改文案或改標記之前，先 grep 那個字串**，正向的斷言會紅（吵，會被發現），
      負向的不會（安靜地死掉）。負向斷言要跟著換成新的標記，不是刪掉。

    - **守門的錯誤路徑從來沒被執行過。**（2026-08-26，`check.sh`）
      兩條守門的失敗訊息寫成 `bad "...（$e）"` —— 全形括號緊接變數名，
      bash 3.2 在 UTF-8 locale 下把括號的延續位元組併進變數名，
      在 `set -u` 之下引用到一個不存在的變數，**整支腳本當場中止**。

      重點不是那個 bash 陷阱，是它為什麼躲得過：**那一行只在守門真的抓到東西的
      時候才會執行。** 你每天跑 `check.sh`、每次全綠，那條錯誤路徑一次都沒跑過。
      直到某天某條守門真的抓到東西，腳本在那一刻中止 ——
      而你會以為是守門壞了，不是它抓到了。

      **判準：守門的錯誤路徑，跟正常路徑一樣要被執行過。**
      反向驗證不是「確認它會抓」，是「**確認它抓到之後的行為是對的**」。

      補記：為了防這件事而新寫的那條守門，**第一版又踩了同一類坑** ——
      pattern 寫成「變數後面接**左**括號」，而真正的 bug 是右括號，
      對注入的違規行完全抓不到。發生在專門為了防這件事而寫的守門上。

    **還有一種更難發現的：測試本身是對的，但它在錯誤的世界裡跑。**
    2026-08-26 驗證上面那條改寫後的守門時，做法是「把 `src/data.js` 改壞、
    跑守門、確認 FAIL」。四個破壞案例全部回 ok —— 看起來像新守門是壞的。
    真相是**當時另一個人正在同一棵工作樹上改那個檔案**，破壞用的字串替換
    找不到舊字面，於是什麼都沒改到，四次跑的都是同一份正常的檔案。

    這一種的斷言沒有錯、程式也沒有錯，錯的是「被測的東西不是你以為的那個」。
    判準：**反向測試一律在自己控制的乾淨副本上跑，不要對共用的工作樹做破壞性
    操作。** 破壞之前先 `git status`，看到不是自己的改動就換地方做。

    **同一種病的第二個形狀：破壞落在別的地方。**（2026-09-01，非幹部頁）
    新加了一條測試「非幹部頁不准出現 `role`」，反向驗證時用
    `perl -0pi -e 's/(<label><i>邀請碼)/<input name="role">$1/'` 注入違規，
    結果測試**照樣全過** —— 看起來像那條測試沒用。真相是那個字串在
    `authHTML` 與 `notCadreHTML` 各有一份，而 `s///` 沒加 `/g` 只改了第一個，
    也就是**沒有被測的那一頁**。乾淨副本、`git status` 都沒問題，
    問題出在「破壞的目標」跟「測試的目標」不是同一個東西。

    **判準：反向驗證的第一步不是跑測試，是確認破壞真的生效了。**
    先讓破壞落地、再確認它落在被測的那一段（diff 一下、或直接印出那一段），
    然後才跑測試。順序反過來的話，「全過」有兩種解釋 ——
    測試無效、或破壞沒發生 —— 而你分不出是哪一種，還會傾向相信前者。

    做法上：破壞用的 pattern 要錨定到**被測對象自己獨有的字面**
    （上面那次改成錨定 `id="ci"` 就對了），不要用兩個地方都有的字串。
    自動化的反向驗證框架，每個案例都應該先回報「破壞改到了／沒改到」。

    ### 測試沒紅有三種可能，第三種最容易被漏掉

    > **破壞了卻沒有變紅，可能是：(1) 測試爛，(2) 破壞沒生效，
    > (3) 那個危險根本不存在。**
    > **第三種最容易被漏掉，因為它長得跟第一種一模一樣。**

    前兩種上面都講過了。第三種是：你在註解或腦子裡寫下「不能這樣做，會出事」，
    而那句話本身是錯的 —— 那個寫法其實沒有問題。這時候把它改成「壞」的版本，
    測試當然不會紅，**因為根本沒有壞掉的東西**。

    2026-09-02 的實例。`weekdayOf` 上面我寫了一段註解：「不能用
    `new Date(y, m-1, d).getDay()`，那會吃執行環境的時區，在 UTC+8 以外的地方
    會差一天。」反向驗證時把實作換成那個寫法 —— **全綠**。第一反應是「測試不夠嚴，
    我的環境時區沒有真的被換掉」，於是把測試改成開子行程真的設 `TZ`。
    **還是全綠。**

    查下去才發現：那句註解是錯的。`new Date(y, m-1, d)` 建的是**當地**的零點，
    `.getDay()` 讀的也是**當地**星期 —— 兩邊同一個時區，任何地方都回同一個答案。
    真正的陷阱是**混用**：用 `Date.UTC` 建、卻用 `.getDay()` 讀（或反過來），
    那才會差一天。註解描述的危險不存在，而我花了兩輪去加強一條本來就沒問題的測試。

    **怎麼分辨第一種與第三種：** 停下來寫出「這個破壞會讓誰、在什麼情況下、
    看到什麼錯的東西」。寫得出具體場景就是第一種（測試該補）；
    寫到一半發現寫不出來，就是第三種（該改的是那句話，不是測試）。
    這一步只要三十秒，而跳過它的代價是為一個不存在的危險加防護，
    然後那道防護會留在程式裡，讓下一個人也相信那個危險存在。

    最後那句是這一項真正的重點：**錯的註解比沒有註解貴**，
    因為它會讓後面每一個人都繞同一個彎。

    **這一項對量測一樣成立。** 2026-08-26 入境章的字級是量過的 —— 但量的是
    `TAIPEI`（6 個字母）。最長的城市是 `SALT LAKE CITY`（14 個），而旋轉 -11 度
    之後外接框的高 = 寬·sin11 + 高·cos11，城市名一長框就變高，往下切進活動格子。
    量了，但**量的是最容易過的那個案例**。挑量測案例的時候問同一個問題：
    什麼樣的輸入會讓這個數字變成最壞？

    這一項的前提（第 11 項的做法）是「壞掉的方式永遠比斷言的方式多」。
    那個前提不會消失，所以這一項不會過期。

13. **「按了沒反應」出現過三次，根因每次都不一樣，症狀每次都一樣。**

    2026-09-02 一天之內，時間看板上出現三次同一個回報：
    「我做了一個動作，畫面完全不動，也沒有任何訊息。」根因彼此無關 ——

    - **請求被權限擋掉。** 知情同意用了 `.upsert()`，而 PostgREST 的 upsert 會把
      主鍵一起寫進 `ON CONFLICT DO UPDATE`，那張表只有 `grant update (notice_seen_at)`，
      整句被拒。錯誤有被 catch，但那一頁的模板根本不收訊息參數，
      所以 `render()` 畫出一模一樣的畫面。
    - **內容在畫面外。** 團隊看板的格子全部正確地畫出來了，但第一格在第 38 列，
      也就是容器頂端往下 600 多 px，而容器一次只看得到二十幾列。
      使用者看到一片空的凌晨。
    - **判斷式把自己人排除掉。** 彈窗的關閉鍵條件寫成
      `!e.target.closest("[data-stop]")`，而 `data-stop` 就掛在關閉鍵的祖先上。
      事件有觸發、狀態沒改。

    三次的修法完全不同，所以這一項**不是一條規則**，它是一個觀察：

    > **每一次都有一條「什麼都不做」的路徑，而那條路徑沒有出口。**

    catch 到錯誤但畫不出來、內容存在但看不到、條件不成立就直接 `return` ——
    形狀不同，共同點是程式走完了一條路，而使用者那一端什麼都沒發生。

    ### 檢查方法：做完一個互動，走一次「什麼都不發生」的那條路

    做完一個互動之後問自己：**有沒有一條路會什麼都不發生？** 然後**真的走一次**。

    問的時候把三種都想過：請求失敗會怎樣、結果是空的會怎樣、條件不成立會怎樣。
    走的時候不要只讀程式碼 —— 這三次裡有兩次是讀程式碼看不出來的
    （一次要看資料庫的授權，一次要在真瀏覽器裡點下去）。

    **這一項刻意不做成守門。** 可以寫一條「每個 `data-act` 分支都必須改到狀態
    或說出一句話」的檢查，但那會逼一些本來就該安靜的分支加東西，
    而一條會製造噪音的守門，最後會被人為了過關而放寬 ——
    這個 repo 已經發生過那件事。不是每一個教訓都該變成機器檢查；
    有些該留在「做完要問的問題」這一層。

14. **「置中」不是中立的選擇，它假設重要的東西在中間。**

    2026-09-02 裁官網那張大合照。原圖 4:3，要裁成 3:2，程式算出來是「上下各切
    168px」—— 數學上沒有錯，而且看起來是最不偏頗的做法。裁完打開圖才發現：
    **下緣切進了前排坐著那幾個人的鞋子。** 天花板那 168px 是燈具與管線，
    地板那 168px 是人。

    改成全部從上面切 336px，鞋子與地板完整保住，燈具也還在 —— 兩邊都沒有損失。
    置中那個「公平」的做法，是唯一一個會切到人的做法。

    **判準：量測算出來的框，跟看起來對不對，是兩件事。**
    裁切、縮放、版面計算都一樣：算出來的數字只保證比例，不保證重要的東西在裡面。
    每一次自動裁切之後**要打開圖看一眼**，而且要問「這個方向切掉的是什麼」，
    不是「切掉了多少」。

    這一項跟第 12 項是同一個形狀，只是換到視覺上：斷言（比例是 3:2）成立，
    而它想守的事（人都在畫面裡）沒有被斷言到。

## 怎麼發新邀請碼

沒有邀請碼就沒辦法註冊，這是擋住外人的唯一一道門。

1. Supabase → **Table Editor** → `invite_codes`
2. 點 **Insert** → **Insert row**
3. 填三欄：
   - `code`：碼本身。建議好念好打，例如 `bt-curriculum-01`
   - `uses_left`：可以用幾次。**發給一個人就填 1**
   - `note`：發給誰，寫給人看的，例如「給課程組小明」
4. Save

**大小寫不算數，前後空白也不算數。** `bt2026test`、`BT2026TEST`、`  Bt2026Test  `
系統都當成同一組碼，所以你用什麼大小寫建碼都可以，學生打成什麼樣也都對得到。

也因為這樣，**不能同時建兩組只差在大小寫的碼**（`bt2026test` 和 `BT2026TEST`）——
資料庫會擋下來，因為那兩組正規化之後長得一樣，系統分不出該扣哪一組。

建議一律用同一種寫法（例如全小寫、用連字號分段：`bt-curriculum-01`），
並且**用複製貼上的方式把碼給學生**，不要用口頭或截圖 —— 打錯一個字母還是進不來，
而畫面上的訊息只會說「這個邀請碼不對」，不會告訴他錯在哪個字。

一組碼給一個人。要發給五個人就建五列，不要建一列 `uses_left = 5` ——
那樣沒辦法知道是誰用掉的。

碼用完之後 `uses_left` 會自動變成 0，那一列可以留著當紀錄。

### 不用發備用碼

**失敗的註冊不會消耗邀請碼。**（2026-08-17 在正式專案實測過，不是猜的。）

- 邀請碼已經用完

### 三條新守門，還有它們各自在防什麼

| 守門 | 防的是 |
|---|---|
| 島的座標必須跟 `scripts/taiwan/coastline.txt` 一模一樣 | 有人就地手改那串四千字的數字。改了之後重跑腳本會蓋掉，或兩邊從此不一樣而畫面看起來都正常 |
| GSAP 兩支都要有正確的 `integrity` 與 `crossorigin` | CDN 上的檔案被換掉。雜湊寫死在 `check.sh` 裡，升級 GSAP 要同時改三個地方 |
| `gsap` 只准出現在 `motion()` 裡面 | 開了「減少動態效果」卻還是有東西在動 |

最後那條要特別說明。`prefers-reduced-motion` 是無障礙需求不是視覺偏好
（使用者 2026-08-25 的裁定）。護照那邊的動畫是 CSS，`check-motion.mjs` 用 CSSOM
逐條比對得出來；**首頁的動畫是 GSAP，CSS 檢查完全看不到它**。
所以這裡守的是結構：所有動畫都關在 `motion()` 這一個函式裡，
而 `motion()` 只有在使用者沒開減少動態效果時才會被呼叫。
這樣「開了 reduce 還是會動」在結構上就不可能發生。
四項破壞測試（手改座標、拿掉 integrity、在 `motion()` 外面加一行動畫、
把守衛那一行的 reduce 判斷拿掉）四次全部被擋下。

### 島要多大：三個切法都做出來看過

`.isle-wrap` 只有兩個值在控制構圖：`right` 是往右推多少、`height` 是島多高。
2026-09-07 三種都渲染出來比較過：

- 切更多（146svh / -14%）：南北兩端都不見，認不出是台灣，只剩一段海岸。
- 現在這組（122svh / -19%）：認得出來，但裝不下。
- 收更小（104svh / -25%）：留白太多，就不震撼了。

要改構圖就改那兩個值，不要去動 SVG 的 viewBox 或座標。

### 標題為什麼是 JavaScript 拆行的

開場要「一行一行落下」，但 HTML 裡的 `<h1>` 永遠是完整的一句話。
斷句是 JavaScript 量出**實際渲染出來的行**之後才包上去的（`splitLines`）。
不在 HTML 裡寫死三個 `<span>` 的理由有兩個：
換了字級、語言或文案，寫死的斷句就會跑掉而且沒有人會發現；
而且 `check.sh` 的「對外頁不可外洩註解」那條守門是抽取可見文字來比對的，
標題被切成三段之後那句話就不再連續，守門會誤判成文案被吃掉了。

### 這一批實測過的

- 開場結束狀態：標題三行 opacity 都到 1、副標到 1、島 opacity 1 且 transform 歸位、
  兩條軌跡的 `stroke-dashoffset` 都是 0（整圈畫完）、`h1.textContent`
  仍然是「還有別條路，只是沒有人跟你說過。」一字不差。
- 數字遞增：從 0 跑到 250+ / 50 / 100+ / 20+ / 5 / 0，跟 HTML 裡的定稿字串完全相同。
- 開了減少動態效果：ScrollTrigger 0 個、島沒有 transform、軌跡已畫完、
  光暈 opacity 0、數字直接是最終值、標題不拆行。
- 375px：沒有元素溢出，往右捲 300px 之後 `scrollX` 還是 0，
  捲動 600px 之後頂欄的 `top` 還是 0（sticky 沒被破壞）。

**水平溢出用 `overflow-x:clip` 不用 `hidden`。** 島是刻意超出畫面右邊的，
要切掉；但 `hidden` 會讓 `<html>` 變成捲動容器，頂欄的 `position:sticky`
就會**安靜地失效**，只有在手機上捲動才看得出來。`clip` 只切不捲。

### 這一頁的一次互動長什麼樣

4. **飛到了**：航線末端出現箭頭指著落點，落點現身（城市、學校、**國家**），

### 箭頭與國家

**箭頭**有兩個：環繞線的末端一個（那就是 logo 上的那個箭頭），
飛到目的地之後航線末端一個。都是 SVG 的 `<marker>`。

- 只有 `path` 掛得上 marker，`ellipse` 不行 —— 所以環繞線是 `path`，
  `d` 由 `ringPath()` 取樣那個橢圓產生。
- 起點就是終點，箭頭落在起點上，所以**起點的角度決定箭頭在哪裡**。
  用 20 度（島的右邊、外海的空白處）。試過 -60 度，箭頭剛好壓在島的北端，很擠。
- 航線的箭頭是**飛到了才掛上去**的。一開始就掛的話，人還沒飛到，
  箭頭已經插在終點了。
- 航線刻意**少畫最後一小段**，空出來給箭頭；畫到底的話箭頭會整個蓋住落點的圓點。
- ⚠ marker 的內容**不會**繼承那條線的 `stroke`（要自己指定顏色），
  但**會**吃到那條線的 `opacity`。兩邊都調暗會相乘 ——
  第一版環繞線 .26 乘上箭頭 .55 只剩 .14，幾乎看不見。

**國家**是 `community.json` 的 `country` 欄位，中文國名就好。
圖上的落點顯示三行（城市 / 學校 / 國家），卡片與手機的清單也都有。
這一頁刻意沒有世界地圖，所以**國名就是「他走了多遠」唯一的地理座標**。

### 大頭照與介紹

`community.json` 每個人有 `photo` 與 `note` 兩個欄位。
`photo` **留空字串就好** —— 留空會顯示姓氏的單字圖示，畫面一樣完整，
而且不會為了「補一張圖」去放一張沒有取得同意的照片。
⚠ 放真人照片跟公開姓名是同一件事：要本人同意，而且要確認那張照片
在拍攝同意條款的涵蓋範圍內（判準見下面「官網首頁的照片」那一節）。

### 兩個「方格」都拿掉了

引言**沒有底色、框線、圓角與陰影**，直接坐在紙上。
（Paul 的回饋：「我不喜歡那個選中方格」。第一版把引言裝進一張卡片裡，

島上的點與落點是 SVG 群組，瀏覽器預設的焦點框會框出一個**長方形**、

⚠ 要連 `:focus` 一起擋，不能只擋 `:focus-visible`：
`<g tabindex="0">` 不是原生可聚焦的元素，用滑鼠點它時 Chrome 走的是 `:focus`，

### 兩個踩過的坑（都不會報錯，只會安靜地錯）

**一、航線一定要畫在島的後面。** SVG 沒有 z-index，後寫的蓋在上面。
放在島前面的話，從島上學校起飛的那一段會被島的填色整個蓋掉，
看起來像航線是從海岸線上憑空冒出來的。

**二、飛行路徑用直線段取樣，不要用 `Q` 或 `A` 指令。**
Chrome 的 `getTotalLength()` 對曲線指令是近似算的，回報的值比瀏覽器畫虛線時
實際用的短（實測差約 9%）。軌跡的動畫是靠 `stroke-dasharray` 用那個長度畫的，
於是**最後一段永遠畫不出來**，線接不到落點。SVG 的 `pathLength` 也救不了，
它的換算基準就是同一個被低估的值。改成折線（切 48 段，看不出來）之後，
自己算的長度與 `getTotalLength()` 完全一致，問題就消失了。

> 查這個坑的時候 `isPointInStroke()` **給了假警報**：折線修好之後它仍然說
> 98% 的位置不在線上，但放大截圖看線是完整接到落點的。
> 判準是**放大截圖**，不是那個 API。

**刻意不畫世界地圖。** 情緒重點是「他們走得很遠」，不是麥卡托投影。
一條弧線加上一個有名字的落點就是一張導航圖，而且比塞一張世界地圖乾淨得多。
弧線是 SVG path 加 `stroke-dasharray` 自己畫的，沒有用任何地圖套件。

## 隱私政策的視覺（2026-09-07）

用 rgba 調淡的文字要實際算對比，「看起來還讀得到」不等於過得了。

## 語言的選擇要跟著人走（2026-09-07）

點導覽到下一頁時，語言原本會跳回瀏覽器的預設 —— 因為每一頁的判斷只看
`navigator.language`。Paul 回報：「選中英文就待在那裡就好。」

**做法是網址帶 `?lang=`，不是 localStorage。** 順序是：

1. 網址上的 `?lang=` —— 使用者在上一頁選過，那個選擇要跟著他走。
2. 沒有的話才看瀏覽器的語言設定。

為什麼不用 localStorage：**這個站現在完全不在使用者的裝置上存東西。**
讀者包含未成年高中生，「什麼都沒存」是一個值得保住的性質，
而且這樣隱私政策一個字都不用改（存了東西卻不寫在隱私政策裡，比不存更糟）。
代價是網址上會多一段 `?lang=`；附帶的好處是把連結傳給別人時語言也跟著過去。

實作是每一頁頁尾的 `keepLang(l)`：把目前的語言寫進站內每一個連結。
**跳過三種**：外部連結與 `mailto`、純錨點、以及 `app/` ——
那是登入的系統，它自己在讀網址上的 `next` 參數，不要去動它。

已知的小缺口：`/privacy/` 沒有 JavaScript（那是刻意的，見那一頁的註解），
所以從隱私政策點回首頁時語言會回到瀏覽器預設。那一頁本身中英兩版同時顯示，
語言對它沒有意義，所以先不處理。

## 三個小改動（2026-09-07，Paul 回報）

### 一、箭頭跟線接不起來 —— 又是一個安靜地錯

畫面上是「線斷在半空中，箭頭卻在正確的終點上，中間空一段」。

原因：**有 `stroke-dasharray` 的線不可以用 `vector-effect:non-scaling-stroke`。**
`non-scaling-stroke` 會讓虛線的長度用**螢幕像素**計算，
但我們給的長度是 `getTotalLength()` 回傳的**使用者座標**。
alumni 那張圖的 viewBox 是 1200、實際渲染約 1264px，比例 1.05 ——
於是虛線比路徑短了 5%，尾巴永遠畫不出來。而箭頭是 `marker-end`，
它落在路徑真正的最後一個點上，所以看起來就是斷開的。

`.route`、`.spark`、`.orbiter` 三條有虛線的線都拿掉了 `non-scaling-stroke`。
`.orbit`、`.isle`、`.islet` 沒有虛線，留著沒問題。

> 這是同一個家族的第三個坑。前兩個是 `getTotalLength()` 對曲線指令低估長度、
> 以及 `pathLength` 用同一個被低估的值換算。**判準一直都是放大截圖**，
> 不是 `isPointInStroke()`，那個 API 給過假警報。

### 二、首頁英文標題的斷行

`.en h1{max-width:11ch}`。11ch 是量出來的，斷成
`There are / other paths. / No one / told you / about them.`（Paul 指定）。
12ch 以上會變四行、9ch 以下變六行。
跟中文那個 `13ch` 一樣，**這個數字不能照字數推算，改了要實際看一次**。

### 三、`/alumni/` 變成中英雙語

原本它只有中文，所以英文使用者點進去會突然變中文，而且語言鈕整個不見。

- `community.json` 多了 `school_en`、`country_en`、`quote_en`、`note_en`
  四個**選填**欄位。沒填就顯示中文那一份，畫面不會壞。
  `city` 與 `place` 本來就是英文；`name` 兩邊共用（一個人的名字就是他的名字）。
- **切語言的做法是整張圖重畫。** 只換字串的話，島上的標籤、右邊的落點、
  手機的清單、卡片四個地方都要各自處理，漏一個就會半中半英。
  重畫一次最單純，代價是選到一半的人會被清掉 —— 切語言本來就是「重新看一次」。
  ⚠ 所以 `draw()` 開頭一定要先把容器清空，不清的話第二次會疊上去。
- 標點也跟著語言走：英文句子裡放一個全形逗號會很刺眼。
- **島上的標籤改成看學校在島的哪一側決定放左或放右。** 英文校名長很多
  （「宜蘭高中」四個字對 `Yilan Senior High School`），全部往左放的話
  東部那幾所會整條壓在島上。中文版也一起受惠。

## 官網對外功能化：批 6 活動營運（2026-09-08）

資料庫 `supabase/migrations/2026-09-12-event-ops.sql`。目標 9 的最後一批。
入口在 `/admin/` 的申請清單上：「簽到」與「寄一封信」。

### 簽到

`applications` 上的兩欄，**不是另一張表**。一份申請對應一場活動，
一場活動一個人只到不到一次。另開一張表要多一組 RLS、多一次 join、
多一個「有沒有那一列」的分支，換到的是我們用不到的能力。
哪天真的要記多場次（兩天的營隊各簽一次），那時候再開表。

- **只列錄取的人。** 沒錄取的不會來，放進點名單只會讓現場那個人多滑一百列。
- **`checked_in_at` 是 null 不是 false。**「還沒點到」與「點過了而且沒來」
  在現場是兩回事，中途才開始點名的那一場，前半段的人全部會是 null。
  要區分靠人知道那一場辦過了，不要在這一欄上發明第三種值。
- 點一個人**只改記憶體裡那一筆，不重讀整份名單**。現場點名是一個接一個點的，
  每點一個就重讀一百列，網路不好的場地會變成點一下等三秒。

### 行前信與通知

一個功能兩個用途：對一場活動的某一群人寄一封信。純文字，沒有排版工具。

⚠ **`send_notice()` 的參數裡沒有收件人**，只有「哪一場活動」與「哪幾種狀態」。
收件人由資料庫自己從 `applications` 撈。
有收件人參數的話，這支函式就是一台任何幹部都能用的群發機 ——
**而它跟正確的版本只差一個參數。**

信一樣先落地成 `mail_outbox`，跟錄取通知走同一條路，
所以「還有 N 封沒寄出去」那一塊照樣看得到。

收信人的名字與信尾那兩句由系統加，畫面上寫著「你只要寫中間那一段」——
不然會有人自己再寫一次署名。

## 官網對外功能化：批 5 資源庫（2026-09-08）

資料庫 `supabase/migrations/2026-09-11-resources.sql`。
新增對外頁 `/resources/`，後台在 `/admin/` 的「資源」那個分頁。

### 目錄，不是檔案主機

這張表存的是**一條連結**，不是檔案。檔案留在 BT 本來就在用的地方
（Google Drive、YouTube、Canva）。

放進 repo 的話，新增一份資源就變成「上傳檔案到 GitHub 再改一個 JSON」，
那正是不能交給每年換屆的 Director 做的事。
放 Supabase Storage 是另一個工程，而那些檔案本來就已經在 Drive 裡了。

⚠ **代價**：Drive 的分享權限設錯就是外洩或打不開，而網站看不出來。
所以後台的編輯頁上有一句「發布之前用無痕視窗自己點一次」，
`test/resources-ui.test.mjs` 有一條在守那句話還在不在。**這是人的流程，不是程式。**

### 標題公開、連結要登入 —— 切在欄位上，不是切在列上

Paul 2026-09-07：「要登入 畢竟我還是要知道是誰跟哪裡人」。

但全部鎖起來的話 Google 就搜不到，而「一個高中生半夜搜『美國大學 申請文書
怎麼寫』搜到 BT」是外人找到這個組織最有效的路。所以：

- **標題與介紹公開**（`blurb` 那一欄是搜尋引擎唯一看得到的東西，
  所以後台那一格的說明寫著「寫給一個第一次聽到 BT 的高中生看」）
- **只有 `url` 那一欄要登入**

⚠ **RLS 做不到這件事，這裡用的是 Postgres 的欄位授權**：
`grant select (除了 url 以外的欄位) to anon`、`grant select on … to authenticated`。
anon 去 select url 會直接被資料庫拒絕。

**前端因此有兩份欄位清單（`PUBLIC_COLS` 與 `MEMBER_COLS`），刻意不共用。**
共用一份的話，遲早有人為了順手把 url 加進去 —— 兩道門要各自成立。

加了「資源」之後是八項：現在開放、資源、關於我們、計畫、做過什麼、Alumni、團隊、合作。

**先縮字級與間距，再換漢堡。** 量出來的：英文版八項在 1180px 剛好放得下，
再窄就縮字級；到 900px 才換成漢堡選單。
1100px 就直接換漢堡對一台筆電來說太早了。
九個對外頁面各自有一份樣式，所以那段 media query 是九份 ——
**改的時候九份都要改**（這就是「外殼各自一份」的代價，也是它換來的：
改壞一頁不會連累其他八頁）。

## 官網對外功能化：批 4 審核與信（2026-09-08）

資料庫 `supabase/migrations/2026-09-10-decisions-and-mail.sql`。
**這一支跑完之後還要做兩件手動設定，不做的話信會安靜地寄不出去**，
步驟寫在那份檔案的最後面（開 pg_net、在 Vault 放兩個 secret）。

### 三顆按鈕，一次可以處理很多人

`/admin/` 的申請清單可以勾選，然後一次標成「邀請面試 / 錄取 / 婉拒」。
一筆一筆按一百次的介面，第五十次就會有人按錯。

**只有 Director 與 President 按得動。** 一般幹部看得到申請，但那三顆按鈕不存在。
2026-09-07 拍板：寄出去收不回來，而 team 裡可能有高一的幹部。
`decide_applications()` **每一筆各自檢查權限** —— 一次傳一百個 id 進來、
其中夾一個別的 team 的，只檢查第一筆的話那一筆就會被偷偷改掉。

**狀態沒有變就不做事，也不寄信。** 這是防連點的核心：
按兩次「錄取」不會寄兩封「恭喜錄取」。

### 為什麼要 outbox

**因為寄信會失敗，而失敗必須看得見。**

直接寄的話，網路斷一秒、Resend 回一個 429，那封「恭喜錄取」就永遠不存在了，
而後台上那個人的狀態明明是「已錄取」。沒有人會發現，
直到那個高中生三個星期後寫信來問「我是不是沒上」。

所以每一封信先落地成 `mail_outbox` 的一列，寄成功才蓋 `sent_at`。
狀態改成功是一件事，信寄不出去是另一件事，兩件分開，各自誠實。
後台上「還有 N 封沒寄出去」與失敗原因看得到，**而且沒有待寄的信就完全不畫那一塊** ——
一個永遠顯示「0 封待寄」的區塊只是雜訊，久了沒有人會看它。

### 為什麼用 pg_net 從資料庫寄，不做 Edge Function

Edge Function 要用 supabase CLI 部署，那是這個 repo 沒有的一道步驟，
而北極星是「換屆的幹部接得住」。多一道部署步驟就多一個沒有人會的東西。

**代價要說清楚**：這一段是整個系統裡最看不見的地方。
所以 outbox 上有 `error` 與 `tries` 兩欄、後台看得到、而且可以按重試 ——
沒有那兩欄的話這個取捨就不成立。

⚠ **`sent_at` 的意思是「送進佇列了」，不是「對方收到了」。**
pg_net 是非同步的，函式拿到的是請求 id 不是結果。
真正的退信只有 Resend 的後台看得到。

### 家長告知信掛在 trigger 上，不是寫在送出的函式裡

理由：**以後如果多了一條建立申請的路，這封信不會漏掉。**
寫在函式裡就等於「記得也要寄信」，而那種記憶會失效。

沒填家長信箱就什麼都不做。填錯或亂填不擋申請（2026-09-07 拍板）：
寄不出去就算了，不要因為這個卡住一個高中生的申請。

### 信的內容

純文字，沒有 HTML，理由跟 `supabase/email-templates/README.md` 那三條一樣。
每一封都有「不要回覆這封信」那一句 —— **那是必要資訊，不是禮貌用語**，
noreply 沒有 MX，按回覆會被退回，而那個人只會覺得沒有人理他。

婉拒信裡有一句「名額有限，而每一年報名的人都比名額多，所以這不代表你寫得不好」。
那一句是刻意的：收信的是高中生。

### 錯誤代碼翻成人話

`admin/src/data.js` 的 `says()`。看到 `mail_not_configured` 的人多半是一個
沒有設定過 Vault 的學生，他需要知道的是「去哪裡做什麼」，不是那個代碼長什麼樣。
**沒對到的錯誤原樣顯示，不要吞掉。**

### 這一批踩到的一件事

`.chips` 與 `.chip` 在 `availability/index.html` 裡屬於「批次填寫」那一段，
而 `admin/index.html` 的外殼是從它的**前半段**複製過來的，所以那兩條沒跟著過來。
篩選那一排看起來像四段純文字，沒有人知道可以點。
複製外殼的時候要確認自己用到的 class 都在複製範圍裡。

## 官網對外功能化：批 3 申請核心（2026-09-08）

目標 9 的第三批，也是整個目標裡最大的一塊。
資料庫 `supabase/migrations/2026-09-09-applications.sql`，**先跑批 2 那一份**。

### 三個新東西

- **`/apply/`（對外）** 列出現在收件中的申請，分成「給高中生的計畫」與
  「加入我們的團隊」兩區 —— 那兩區的讀者不是同一群人。
  **沒登入也看得到題目**，只是填不了。這一頁是給路人看的，
  要能先看過再決定要不要開帳號。
- **`/admin/`（登入後）** 開表單、改題目。四種題型，上下移動，狀態三種。
- **`/app/` 的學員頁**多了「我的申請」與「現在開放」兩區。

### 資料的形狀：表單屬於 team

2026-09-07 Paul 的原話「每個 team 申請表也都不一樣呀」。
所以所屬計畫**是結構本身，不是附加欄位**：
表單屬於一個 team → 申請屬於一份表單 → 權限跟著表單的 team 走。
換屆換人不換設計，因為 team 的名字比人的名字穩定。

### 三件事一定要照這樣做，改之前先讀

**一、申請存的是送出當下的快照。**
`applications` 有 `applicant_name` / `school` / `grade` / `email`，
那些 `profiles` 裡也有，看起來重複。三個理由：審核要看他**當時**填的
（三月申請時是高二，六月改成高三，審核紀錄不該跟著變）；
幹部讀不到學員的 `profiles`，不存快照就得為了顯示名字而放寬一整張表的可見範圍；
以及這張表自足，要匯出、要交接一張表就夠。

**二、送出走 `submit_application()`，不是 insert。**
**email 一定要由伺服器填。** 前端填得動的話，一個人可以把別人的信箱
寫進自己的申請，而我們之後會朝那個信箱寄「恭喜錄取」。
那不是理論風險，那是一封寄給無關的人的信。
順帶讓「必填有沒有填」與「表單開放中沒有」在伺服器這一端也各檢查一次 ——
前端那兩份是為了讓他當下就看到，不是門。

**三、同一份表單送第二次不是錯誤。**
他按了兩下、或開了兩個分頁。函式接住 `unique_violation`，
回原本那一筆的 id，畫面就跟第一次送出一模一樣。

### 可見範圍（2026-09-07 拍板）

一份申請**只有那份表單所屬 team 的幹部看得到**，不是所有幹部。
三十個幹部裡有高中生，而申請人可能是同校學弟妹。
「我在後台看到我認識的人寫他爸媽不支持他出國」發生一次，
就再也收不到誠實的申請。**這跟護照的隱私界線是同一件事。**

「看得到」與「改得動」故意差一級：一般幹部看得到自己 team 的申請，
但開表單、改題目是 Director 與 President 的事。
`/admin/` 對一般幹部是唯讀的，而且畫面上說出為什麼。

### 這一批踩到的三件事

- **★ 只有日期的字串不可以交給 `new Date()`。**
  `"2026-12-15"` 會被當成 UTC 午夜，再用本地的 `getDate()` 讀出來，
  在台灣以西的時區就少一天 —— 而畫面上那是一個看起來完全正常的日期。
  2026-09-08 實測：headless Chrome（美西時區）把 12/15 畫成 12/14。
  `apply/src/ui.js` 的 `fmtDate` 與 `app/src/ui.js` 的 `fmtDay` 都特判了，
  `test/apply-ui.test.mjs` 有一條守著。
- **「必填」不可以用橘色。** #FFC46C 在米白上大約 1.5:1，那兩個字等於看不見。
  這個 repo 已經在六個地方踩過「用顏色當唯一訊息」。
  必填這件事本來就是那兩個字在講，不是顏色在講。
- **`.q > label` 會選到選項。** 單選與多選的每一個選項本身也是 `<label>`，
  而且是 `.q` 的直接子元素。不加 `:not(.opt)` 的話整排選項會跟題目一樣粗，
  題目與選項就分不出層次。

### 刻意沒做

`form_questions` **沒有** `unique(form_id, ord)`。上下移動題目時中間一定會有
一瞬間撞號，有 unique 就要先搬到暫時號碼再搬回來 —— 三句 SQL 換一個
沒有人在意的性質。撞號時的表現是「兩題順序不定」，不是「存不進去」。

`applications` **沒有 insert 與 delete 政策**：送出只能走函式，
申請跟著帳號走，刪帳號才會一起消失。

批 1 時它指向 `/programs/`（因為 `/apply/` 還不存在），現在指向 `/apply/`。
`join/index.html` 裡有三個地方（meta refresh、`location.replace`、看得見的連結），
**三個都改了**。`programs/index.html` 那兩顆按鈕也從 Instagram 改回站內。

三層，對得上 BT 的組織形狀：`member` / `director` / `president`。

**跟 `role`（cadre / student / alumni）是兩件事。**
`role` 說「他是不是幹部」，`board_role` 說「他在幹部裡管到哪」。

是一個假設，不是一道門。

**「看得到」與「按得下去」故意差一級。** 該 team 的成員看得到自己 team 的申請，
但會寄信的那幾顆按鈕只有 Director 與 President 有。
寄出去收不回來，而 team 裡可能有高一的幹部。

要改只能透過 `set_board_role()`，而它只有 president 叫得動，
**而且擋住自我降級** —— 兩位 Co-President 其中一位手滑把自己降級、
另一位剛好聯絡不上的話，這個系統就再也沒有人能發權限，只能回去下 SQL。

### 學校清單

`app/schools.json`，506 間一般高級中等學校，由
`node scripts/schools/build.mjs` 從教育部統計處的名錄產生，**一學年重跑一次**
（學年度寫在腳本裡的 `YEAR`）。網路不通的機器可以先 `curl` 下來再
`node scripts/schools/build.mjs <檔案>`。

- **不是外鍵，是自由文字。** 清單外的學校（高職、海外、實驗教育）一定會出現，
  做成外鍵就等於把那些人擋在門外，而他們正是最需要這個資訊的人。
- **只有同名的學校後面補縣市。**（不同縣市真的各有一間「市立中山高中」。）
  自動完成上出現兩個一模一樣的選項，使用者只能亂猜，而我們也分不出是哪一間。
- 清單是**點進那一格才載**的，47KB 不值得讓每個來登入的人都下載一次。
  載不到就是一個普通文字欄位，**這件事不對使用者說任何話** —— 對他來說沒有壞掉。

### 為什麼四個欄位是登入之後才問，不是註冊表單上問

三個理由，寫下來免得有人「順手」把它搬回註冊表單：

1. 用 Google 進來的人根本不會經過註冊表單。兩條路各問一次就有兩份要維護的欄位。
2. email + 密碼註冊要先收確認信才登得進來，那個時間點還寫不進 `profiles`。
3. **電子報那個勾在補完資料頁才有意義**，因為旁邊就寫著我們拿它做什麼。
   夾在註冊表單的密碼欄下面沒有人會讀。

⚠ **那個勾預設不打。預設打勾等於沒有同意。** `test/student-ui.test.mjs` 守著。

### 刪除帳號

`delete_my_account()`，沒有參數，身分只有 `auth.uid()` 一個來源。
**刪的是 `auth.users`**，一路 cascade 下去；只刪 `profiles` 的話他用同一個 email
再登入會拿到一個沒有 profiles 的殭屍帳號，什麼都做不了而且自己修不了。

前端要**打字確認**，不是按兩次。按兩次擋不住誤按，因為誤按的人第二次也會按。

這個按鈕不是加分項。2026-09-07 Paul 決定申請資料不設保存期限，
**那個決定的對價就是當事人隨時拿得回控制權**，寫在隱私政策裡叫人來信不算數。

幹部走不到這一條（函式裡擋著）：護照有蓋章紀錄與別人看得到的進度，
幹部要離開是換屆交接的事，不是一個按鈕。

## 全站的點擊回饋（2026-09-08）

Paul：「我要 UIUX 很好，點擊會有回饋」。盤點結果：**全站零個 `:active`**，
而且五個登入後的頁面設了 `-webkit-tap-highlight-color:transparent` ——
那一行把手機上唯一的預設回饋關掉了。**那五頁在手機上按下去，畫面完全不動。**
而畫面不動的時候，使用者會再按一次。

### 加了什麼

十七頁各一份（外殼各自一份的代價，`check.sh` 有一條守誰漏了）：

| 元素 | 按著的樣子 |
|---|---|
| 所有 `button` 與看起來像按鈕的 `a` | 縮到 97% |
| 實心主要按鈕 | 再暗一階（`brightness(.88)`） |
| 框線鈕、chip、語言鈕、登出 | 底色變成橘色 38% |
| 已選中的 chip | 亮一階（不是蓋淺色，那會像取消選取） |
| 單選、多選、勾選框那一整行 | 底色變成橘色 26% |
| 內文裡的連結 | 底線變橘色（**不縮放** —— 那會讓一段字在按的時候跳動） |

### 三個判斷

**不給它 `transition`。** 按下去的回饋要**立刻**發生；加了過渡就變成
「按了之後才慢慢縮」，那比沒有回饋更像卡住。
（也因此它不是「會動位置的過渡」，對 `prefers-reduced-motion` 沒有意義 ——
按鍵回饋不是前庭刺激來源。）

**用橘色不用深藍調淡。** 深藍 12% 在米白上讀起來是**冷灰**，而整站是暖的 ——
那一下按壓會看起來像變髒，不像有回應。橘色本來就是這個品牌
「正在動的東西」的顏色，而正在被按的就是那個東西。

**整行可以點的東西要自己處理。** 單選與多選的每一項是 `<label>` 不是 `<button>`，
`button:active` 抓不到它們，而**那是手機上最常按的東西**。

⚠ **誤報的守門會被人習慣性忽略，久了真的漏掉也不會有人看。**

## 信件文案改成後台編輯得動（2026-09-08）

四封信的文字原本寫死在 `mail_body()` 裡，改一句話要跑一支遷移檔。
對 Paul 沒差，但對明年那個幹部來說，「改一句信的文案」變成要碰 SQL ——
**那跟北極星（換屆的幹部接得住）是有張力的。**

`supabase/migrations/2026-09-16-mail-templates.sql` 把文案搬進 `mail_templates` 表，
`/admin/` 多一個「信件文案」分頁。

### 三個刻意的限制

**一、信尾那一段不給改。**「不要回覆這封信，這個信箱沒有人看」是必要資訊，
不是禮貌用語 —— noreply 沒有 MX，按回覆會被退回，而那個人只會覺得沒有人理他。
由 `mail_tail()` 加在每一封的最後面。編輯頁上看得到它，但它是灰的，
而且畫面上明講「這一段改不掉」——不說的話人會以為自己刪得掉。

**二、讀不到就退回寫死的那一份。** 有人手滑刪掉一列、或這張表還沒建起來的時候，
信照樣寄得出去。**寄不出「恭喜錄取」的成本，遠高於那封信用的是舊文案。**
退路刻意只留最短的一份 —— 它的工作是「信寄得出去」，不是好看。

**三、只有 Co-President 改得動。** 這四封是全組織對外的聲音，
不是某個 team 自己的東西。六個 team 各自改一句，那四封信就會慢慢變成六種語氣。

### 這一頁的價值全在預覽

代換符號（`{姓名}`、`{活動名稱}`）打錯不會壞掉，**只會空著**。
預覽是唯一會當場讓人看到「我把 `{姓名}` 打成 `{名字}` 了」的東西。

- 打字就更新，而且**只重畫預覽那一塊，不整頁 render** —— 整頁重畫會把游標彈回開頭。
- 前端的 `fillMail()` 跟資料庫的 `mail_fill()` **必須是同一套規則**。
  兩邊不一致的話預覽就會騙人，而**預覽騙人比沒有預覽糟**。
- 連預覽裡那個空行都要對：信裡的信尾前面真的有一個空行，
  但預覽拆成兩個 `<pre>` 會把它吃掉，所以用 `margin-top:1.75em` 補回來。

### 主旨也要跟著表走

`queue_guardian_notice()` 與 `decide_applications()` 裡原本寫死主旨，一起換成
`mail_subject()`。**不換的話文案只改得動一半** —— 內文跟著表、主旨還是舊的，
而那種半套最難發現：改了主旨按存檔一切正常，直到信寄出去才看得到。

## 登入那幾頁的四個修正（2026-09-08，Paul 實測回報）

四件都是同一類：**系統做對了事，但沒有告訴使用者。**

### 一、註冊完什麼都沒說

開了 email 確認之後，`signUp` 成功但**不會登入**（`data.session` 是 `null`）。
舊版在那裡直接 `boot()`，而 `boot()` 找不到使用者就把同一張登入表單再畫一次 ——
看起來就像按了沒反應。

現在多一個 `check` 畫面：「去收一封信」，說得出寄到哪個信箱、
先看垃圾郵件匣、還有一條回登入的路。
**沒有回應的送出，使用者只會再按一次。** 這是這個 repo 一路上最常見的失敗形狀。

### 二、email 已經有帳號 → 直接帶回登入畫面

`shared/auth.js` 的 `signUp` 本來就認得出重複的 email（兩種形狀都認），
但舊版只是丟一句話給使用者，要他自己按「我已經有帳號了」再重打一次 email。
現在直接切到登入模式、email 留著、訊息說「直接登入就好，密碼忘記的話下面可以重設」。

`shared/auth.js` 轉出一個 `MSG_DUP_EMAIL` 給前端比對。
比對字串是難看的，但比在 `main.js` 再抄一份那句文案好 ——
抄一份的話，改文案的人不會知道有第二個地方在對這句話。

### 三、密碼打錯不要清掉 email

登入、註冊、忘記密碼三頁的 email 欄位都會把上次打的字帶回來，**密碼不帶**。
切換登入／註冊的時候也不清掉。

密碼打錯就要重打一次 email，是在懲罰一個本來就已經有點挫折的人；
而且他重打的時候可能會打錯，於是錯誤訊息從「密碼不對」變成「查無此人」，
他就更找不到問題在哪。

### 四、送出中沒有任何狀態

登入、註冊、寄重設連結三顆按鈕，送出中會鎖住而且字會變。
沒有這個狀態的話，網路慢的時候畫面完全不動，而使用者會再按一次。

### 重設密碼的信「不 work」時要看哪裡

前端這一端沒有東西可以修 —— `resetPasswordForEmail` 有錯就會顯示出來，
而那一頁**不會**告訴你這個信箱有沒有帳號（那是刻意的，`check.sh` 有一條在守，
不然任何人都能拿那個表單一次一個 email 問「這個人是不是 BT 幹部」）。

所以「按了說寄出去了但信沒來」要往 Supabase 查，照這個順序：

1. **Authentication → URL Configuration → Redirect URLs**
   本機測試要加 `http://localhost:8000/**`。
   **不在名單上的話，信裡的連結會被導回 Site URL**（線上的網站），
   點下去就不是你本機那一頁 —— 看起來很像「連結壞了」。
2. **Authentication → Logs**：看那一封到底有沒有被送出去。
3. **Resend 後台 → Logs**：看它有沒有被退信或進垃圾桶。
4. **寄信頻率上限**。Supabase 對重設密碼信有速率限制，
   同一個信箱短時間內要第三、第四封會被靜靜擋掉。
   測試的時候很容易撞到 —— 換一個信箱，或等一小時。

### 一個「驗不到」立刻就變成 bug 的例子（2026-09-08）

第一版的腳本整支用超級使用者跑，而**超級使用者繞過 RLS**，
所以政策一次都沒有被評估。檔頭當時老實寫了「RLS 驗不到」。

那個洞當天就掉出東西：`/apply/` 與 `/resources/` 沒登入時直接顯示
「現在連不上資料庫」。原因是那兩張表的政策會呼叫 `is_on_team()` 與
`is_director_of()`，而那兩支照 `is_cadre()` 的樣子把 `anon` 的執行權限收掉了 ——
於是沒登入的人一讀那張表，Postgres 要評估政策、要呼叫那支函式，
而他沒有執行權限，**整個查詢失敗，不是「讀到零列」**。

修法：`supabase/migrations/2026-09-14-anon-execute.sql`，
把那四支發給 `anon`。安全，因為它們回的是「**呼叫者自己**是不是某種身分」的布林值，
對沒登入的人一律回 false —— 他能問到的只有「我不是」。

⚠ **不要靠 `or` 的短路來繞過**（例如 `auth.uid() is not null and is_on_team(...)`）。
規劃器可以自由決定兩邊的評估順序，短路不是保證。

**教訓：「這一段驗不到」寫在註解裡不會讓它變安全，只會讓它變成一個有人簽過名的洞。**
腳本現在會用 `anon` 與 `authenticated` 的身分各讀一次。

### 測試腳本自己的一個坑

`set -euo pipefail` 之下，`psql` 回非零會讓**整支腳本直接結束**，
而不是報一個 FAIL —— 也就是「檢查失敗」變成「後面的檢查安靜地沒跑」。
第一次做破壞測試時，畫面上只是變短，沒有任何一行寫著 FAIL。
每一個斷言的 psql 呼叫後面都補上 `|| true` 了。
**會安靜消失的測試比沒有測試糟。**

### 它驗得到什麼、驗不到什麼

**驗得到**：語法、相依順序，以及那幾支函式自己的判斷邏輯 ——
誰按得動、連點兩次會不會寄兩封、必填留白擋不擋得住、
email 是不是伺服器填的、刪帳號會不會連帶把申請刪乾淨、兩把鑰匙缺一把算不算數。

**驗不到**：真的寄信（`net.http_post` 是替身）、
Supabase 的 `auth.users` 與 Vault 的真實行為、以及 Supabase 自己那一層的設定。
那幾件只有在 Supabase 上照
`docs/2026-09-08-目標9-上線前測試清單.md` 走一次才驗得到。

### 為什麼值得有這一支

寫完那六支遷移檔的時候，它們一行都沒有在資料庫上跑過。
「讀起來對」跟「跑得過」是兩件事。
而且它是**可重跑的**：以後改了任何一支遷移檔，跑一次就知道有沒有弄壞別的。

### 寫這支腳本的時候踩到 repo 自己記錄過的坑

`$got）` —— **shell 變數名後面直接接全形字元**，bash 會把全形字連進變數名，

## 手機版的版面守門：`node scripts/check-mobile.mjs`（2026-09-10）

### 三件當初做錯、後來修好的判準

**一、`chrome --headless --window-size=390,844` 量不到 390。**
macOS 上視窗有最小寬度，實測拿到的 CSS 視寬是 **500**。
畫面看起來會過關，而手機上照樣爆。

**二、判準不能是「有沒有超出視窗」。**
首頁那座島是刻意畫到畫面外、靠 `html{overflow-x:clip}` 切掉的，那是設計；
而頂欄的項目被切掉是 bug。兩者對「有沒有超出視窗」的答案一模一樣。
真正的判準是**「有沒有跑出自己那一排」**：一個橫向的 flex 容器，
它的小孩不該超出它的內容範圍。第一版用前者，把首頁的島報成六個錯，
真正的問題就淹在裡面。

**三、要用登入後的狀態量。**

## 「選單」跟「登出」沒對齊（2026-09-10）

Paul：「我說選單跟登出…」。兩顆並排的藥丸鈕，一顆比另一顆高 7px。

### 原因不在 `shared/nav.css` 裡，在別人的頁面上

那顆選單是一個 `<label>`。而時間看板那一頁自己有一條通用規則：

```css
label{display:block;margin-bottom:14px}
```

那 14px 的下邊界跟著套到共用頂欄的選單上。
`align-items:center` 對齊的是**外框盒（含 margin）**，
所以多了一截下邊界的那顆就整個往上跑 7px（14 的一半）。

**這個 bug 最難的地方是它讓 `align-self` 看起來壞掉。**
把選單設成 `align-self:center`、`flex-end`、把 `.btnav` 設成 `align-items:stretch`
——通通沒有反應，因為它本來就已經置中了，只是盒子多了一截。
繞了很久才想到去看**頁面自己的** CSS。

### 修法兩件

**一、`.btnav > *{margin:0}`。**
共用元件不可以依賴 host 頁面「沒有寫某條通用規則」。
四個頁面各自都有 `label{}` 與 `button{}` 的通用規則，而它們互相不知道對方存在。
這跟護照那邊用 `:where(#bt-root button)` 重設按鈕外觀是同一件事。

**二、登出與選單共用同一份樣式。**
以前選單是 `var(--display)` 15px 700 加字距，登出是 `var(--body)` 14px 600 ——
就算沒有那個 margin，兩顆也是一高一低一粗一細。
兩顆是同一種東西，就該長得一模一樣。
高度靠 `min-height` 加 `inline-flex` 置中，**不要靠 padding 湊** ——
用 padding 湊的話，哪天有人改字體或字級，兩顆又會不一樣高，而且不會報錯。

### 最後那 2px：button 與 label 的預設不一樣

兩顆一樣的藥丸鈕，一顆是 `<button>` 一顆是 `<label>`，
而瀏覽器對它們的預設不同：**button 預設 `border-box`，label 預設 `content-box`**。
同一個 `min-height:38px`，button 是連框線一起 38、label 是框線外再加 2 —— 差 2px。
`line-height` 同理。

四個頁面現在剛好都寫了 `*{box-sizing:border-box}`，所以在真的站上看不出來 ——
**而「剛好」正是之後會壞掉的那種理由**。所以共用的那份樣式自己寫死
`box-sizing:border-box` 與 `line-height:1`，不假設 host 頁面有鋪好地基。
（驗證的時候要用一個**故意沒有**那條通用規則的頁面去量，不然量不到。）

### `check-mobile.mjs` 多了第三種檢查

原本只看「跑出自己那一排」與「疊在一起」，而這個 bug **兩種都不是**：
選單既沒有溢出也沒有重疊，只是看起來歪。

現在多一種 `offcentre`：說好 `align-items:center` 的一排，
裡面每個東西的中心線要跟其他人對得上（容許 3px 的字體度量誤差）。
破壞測試過 —— 把 `.btnav > *{margin:0}` 拿掉，它會報
「nav.btnav 說好置中，但 label.btnav-burger 的中心線差 -7px（選單）」，
跟 Paul 用眼睛看到的是同一件事。

## 頂欄跟頁面內容對不齊（2026-09-10）

Paul：「這兩個怎麼不平行」。頂欄那條藥丸跟底下的分頁列左右差了 16px。

原因是**同一條頂欄被畫在兩種不同的容器裡**：
護照與時間看板把它併進寫給 `#bt-root` 的那串 innerHTML，
申請管理與設定則是 `document.body.insertAdjacentHTML` 到 `<body>`。
`#bt-root` 有自己的左右內距（12px），畫在 body 上的那條吃不到，
而 `shared/nav.css` 又自己加了 16px 的左右 margin（理由是「不然玻璃會貼著螢幕邊」）——
畫在 `#bt-root` 裡的那兩頁就變成 12 + 16 = 28px，比底下所有東西再縮 16px。

修法兩件：**四頁一律把頂欄畫進 `#bt-root`**，然後把 `nav.css` 那條左右 margin 拿掉。
留白由頁面自己的容器負責，頂欄只負責填滿它被放進去的地方。
`check.sh` 有一條在守「不准再 insertAdjacentHTML 到 body」——
畫在 body 上不會壞、不會報錯，只是差十幾 px，而那種差距只有兩條東西並排時才看得出來。

順帶一提，改完之後那兩頁也不用再自己去 `remove()` 上一次那條頂欄了，`innerHTML` 蓋掉了。

### 一個會讓 check.sh 說謊的殘留檔

`scripts/check-mobile.mjs` 會產生四份 `<資料夾>/_audit.html`，跑完自己刪。
中途 Ctrl-C、或單獨跑 `scripts/mobile-fixtures.mjs` 的話那四份會留著，
而它們會被後面每一條「掃過所有 html」的守門看到 ——
2026-09-10 的表現是 `check.sh` 報「§11-20 出現非組織信箱」，
而 repo 裡其實一個字都沒有，那個 email 在假資料裡。
現在 `check.sh` 第一步就先擋殘留檔，訊息才對得上原因。

使用者在同一個網站不用學兩種操作。寬螢幕完全沒有變。

### 三件不要「改良」的事，每一件都試過而且都壞了

**一、開合是純 CSS：一個看不見的 checkbox 加一個 label。**
不要改用 JavaScript。那段程式要嘛塞進四個頁面的 `main.js`
（四份會各自壞掉，而且下一個做新功能的人一定會漏掉），
要嘛讓 `shared/nav.js` 在被 import 的時候偷偷掛一個全域監聽。checkbox 兩者都不用。
checkbox 是移到畫面外、不是 `display:none`，所以鍵盤 tab 得到、讀螢幕唸得出來。

**二、不要改用 `<details>`。** 試過了。`<details>` 在還沒展開的時候會把
`<summary>` 以外的小孩整個藏起來，而那不是一條可以用 CSS 蓋掉的規則
（瀏覽器是用內部的 slot 做的）。結果是**寬螢幕上四個功能項整排消失**，
而且不會報錯 —— 是靠截圖才發現的。`test/nav.test.mjs` 有一條在擋。

**三、面板是實色的，不要改回玻璃。**
頂欄本身有 `backdrop-filter`，而**在一個有 `backdrop-filter` 的元素裡面
再放一個有 `backdrop-filter` 的面板，底下的內容會透出來，
透的程度跟你寫的 alpha 對不起來** —— 背景寫到 `rgba(...,.99)` 了，
畫面上底下那張卡片的標題與 email 還是讀得出來。換成實色底就乾淨了。
面板是拿來讀的，讀不到就是壞的。

### 還有一個跟版面無關、但很花時間的坑

`navHTML` 回傳的是一個樣板字串（template literal），
**裡面的 HTML 註解不要用反引號括程式碼** —— 那會把字串提早結束掉，
而錯誤訊息是離現場很遠的一句 `Unexpected token`。
同一類的還有：HTML 註解裡不要寫出 `script` 標籤（`check.sh` 找程式區塊會誤判），
而測試要檢查「HTML 裡有沒有某個標籤」時，要先把註解剝掉再看

## 頂欄在手機上擠爆的那次（2026-09-08）

Paul 回報「選單跑掉了」：手機上「選單」兩個字被擠到玻璃外面，直立地掛在頂欄右邊。

原因是**登入之後那顆按鈕的字會變長**。登出時是「登入 / Sign in」，
登入之後變成「我的 BT 帳號 / Account」，再加上 logo、語言鈕、選單鈕，
在 390px 的手機上總寬約 386px，而頂欄只有 348px。
這幾個元素都是 `white-space:nowrap`，縮不下去，於是排在最後的選單被推出去。
**沒有任何東西會報錯**，而且只有登入過的人看得到 —— 也就是只有幹部看得到。

### 修法：窄螢幕上那顆按鈕只講一種語言

字被拆成三段 `<span>`：`.lg-a`（中文）、`.lg-sep`（斜線）、`.lg-b`（英文）。
560px 以下，斜線藏起來，然後照 `html[data-lang]` 只留當下那個語言那半。
兩種讀者都還看得懂，寬螢幕上兩半照舊都在。
另外把頂欄間距、logo 高度、按鈕內距各縮一點 —— 只藏一半的話實測只剩 1px 餘裕，
下一次有人動字級就會再擠出去一次。現在中文那半在 390px 上有 44px 餘裕。

**這一段在九個對外頁面各有一份**（外殼各自一份的代價）。改一頁就要改九頁。

### check.sh 跟著改的一條

那條「登入之後要改字」的守門原本找完整的字串「我的 BT 帳號 / Account」，
拆成 span 之後那串字不再連在一起。改成找「我的 BT 帳號」就夠了 ——
這條守門要抓的是「哪一頁整段忘了加」，不是措辭。

### 量測方法（下次要動頂欄的話）

headless Chrome 的視窗最小寬度是 500px，**量不到 390 的手機**。
做法是把手機那幾條規則用 `!important` 強制打開、把 `.topbar` 的寬度直接設成 350px
（390px 手機扣掉左右 gut 之後的實際寬度），再把每個子元素的寬度加起來跟 `clientWidth` 比。
`scrollWidth === clientWidth` 不夠用：頂欄的 logo 有 `margin-right:auto`，
最後一個元素永遠貼著右邊，看起來都「沒有溢出」。

## 首頁的宣傳影片（2026-09-08）

首頁「我們做什麼」跟「誰在做這件事」中間留了一段放宣傳影片。
**現在是空的**，因為還沒有影片。

### 要放影片，只改一個地方

`index.html` 最下面那段程式裡：

```
var VIDEO_ID = "";
```

把 YouTube 的影片編號填進引號裡（網址 `youtube.com/watch?v=XXXXXXXXXXX` 裡 `v=` 後面那一串），
中英兩段就會自己出現。空的就整段不存在。
**不用改 hidden，也不用改程式。** 中英各一段但編號只填一次，是刻意的 ——
填兩次一定有一天只改到一邊。

### 為什麼是「按了才載入」，不是直接嵌一個播放器

直接把 iframe 寫進 HTML 的話，**每一個打開首頁的人**，包含根本不想看影片的人，
都會被 YouTube 記一筆。那一刻 footer 那句「本網站不使用任何追蹤或廣告工具」
與隱私政策就同時變成假的，而畫面上完全看不出差別 —— 影片照樣會播。

所以畫面上先放一塊**本站自己用 CSS 畫的封面**（沒有任何檔案是從站外載的），
按下去才把 iframe 生出來，網域用 `youtube-nocookie.com`。

`check.sh` 有一條在守這件事，兩種常見的「簡化」都會被擋下來：
寫死的 `<iframe>`、以及拿 YouTube 的縮圖網域當封面。
**連寫在註解裡的那個網域都會被抓到**，那是刻意的 —— 註解裡出現，通常表示有人正要那樣做。

隱私政策的第三方表格已經有 YouTube 那一列，寫的是「僅在你按下首頁的播放鍵時」，
放了影片之後不用再改。

### 一個踩過的坑

HTML 註解裡不要寫出開頭是小於號的 `script` 標籤。`check.sh` 找內嵌程式區塊用的是
正規表示式，註解裡的那個標籤會被它當成真的，往下一路吃到下一個結束標籤，
把 GSAP 那兩行也吞進去，然後回報「首頁有動畫跑到 motion() 外面」——
訊息跟真正的原因完全對不上，很難查。

## 團隊頁的人怎麼呈現（2026-09-08）

**一、去背照片不用多開資料庫欄位，靠圖檔格式判斷。**
設定頁上傳大頭照的時候會看有沒有透明像素（`settings/src/main.js` 的 `hasAlpha`）：
有就存成 webp（留得住透明），沒有就存成 jpeg。

以前那支壓縮一律存 jpeg，而 **jpeg 沒有透明這回事** ——
去背照上傳完透明的地方會變成黑色，一個人會變成黑方塊裡的人。

**二、欄數是寫死的 4 / 3 / 2 / 1，不是 `auto-fill`。**
Paul 要的是「互動得拍照」：往右看的人，右邊那個比一個「噠噠」。
`auto-fill` 的話「誰在誰右邊」會隨視窗寬度變，那些姿勢就對不起來。
欄數固定，加上 `team/src/main.js` 用英文名字母序（固定、不用誰維護順序欄位），

**但每個人的姿勢單獨看也要成立**，手機上一排一個，那時候看不到任何連動。

**三、卡片裡不准用 `zh` 或 `en` 當 class 名。**
整站的語言切換是 `html[data-lang="en"] .zh{display:none}`。
中文名那一格第一版取名叫 `zh`，結果英文版把每個人的中文名整個藏起來，
而且不會報錯，只是畫面上少了東西。現在叫 `cname`，測試裡有一條在守。

去背照片超出卡片的高度 = `.cut` 的 `height` 減掉 74px（`bottom:calc(100% - 74px)`），
最多 106px。所以 `.crew` 的 `padding-top` 與 `row-gap` 都不能小於它，
不然第一排的頭會壓在 team 標題上，後面每一排的頭會壓在上一排的名字上。
改照片高度的話這兩個要一起改。

### 還沒有的東西

## 頂欄的 liquid glass（2026-09-07）

Paul 指定的。玻璃不是「半透明」而已，它有四層，缺一層就會變成一塊灰灰的塑膠：

1. **底**：由亮到暗的漸層。光從上面來，所以上緣比下緣亮。
2. **折射**：`backdrop-filter` 的 `blur` 加 `saturate`。
   **`saturate` 是關鍵** —— 只有 `blur` 的話後面的顏色會被洗掉，
   看起來像毛玻璃不像玻璃。
3. **高光**：上緣一條 inset 的白線，那是光打在玻璃邊緣的反光。
4. **影子**：往下的柔影，讓它浮在紙上面而不是貼在紙上。

顏色全部是米白與白的不同透明度，沒有新色（Brand Book 硬規則）。
它是**浮起來**的（左右留白、圓角、離頂端一段距離），不是鋪滿的一條 ——
鋪滿的話玻璃沒有邊，看不出它是一塊材質。

### 兩個實測後調過的值

- **頂欄的不透明度不能再低。** 玻璃浮在內容上面，底下可能是一張深色照片，
  太透的話 logo 與導覽文字會糊掉。玻璃再漂亮，讀不到就是壞的。
- **手機展開的選單面板要比頂欄更不透明**（.93 對 .78）。
  頂欄底下通常是紙色或島，面板展開時底下是內容，可能是一整張照片。
  第一版兩者用同一組值，實測面板上的字整個糊在照片裡。

不支援 `backdrop-filter` 的瀏覽器（舊 Safari、部分 Android）用 `@supports`
退回不透明的紙色 —— 偵測不到卻硬做的話，使用者會看到一塊幾乎透明的東西壓在文字上，
那比沒有玻璃難看得多。

Lighthouse 實測：換成玻璃之後無障礙仍然是 100（對比度沒有被玻璃弄壞）。

**護照與時間看板走的是另一份 `shared/nav.css`。** 那兩頁是登入後的工具，
它的項目來自 `shared/nav.js` 的 FEATURES（登入後才有的功能），
跟這一條給路人看的頂欄是兩個東西，**不要合併** ——
合併之後路人會看到他點不進去的功能。
材質在 2026-09-07 統一成同一塊玻璃（見下面「內部工具的外殼」）。

## 校友與「我的故事」（2026-09-11）

`/alumni/` 那頁航線圖上原本只有示範資料（假名字）。這一批做完之後，
上面的人可以是真的校友或幹部本人填的資料 —— 前提是他自己同意、而且被
Co-President 核可過。**做完程式不等於頁面上有真人**：這張表現在是空的，
要一個一個人核可上去。

### 兩把鑰匙

跟 `/team/` 那一節（「對外團隊頁上的那三十個人」）同一個形狀：一件事要對外公開，
一定要「本人同意」加「P/VP 核可」兩把鑰匙都轉開，缺一把都不行。

| 欄位 | 誰改得動 | 在哪裡 |
|---|---|---|
| `public_story`（本人同意公開） | **本人自己** | `/settings/` 的「我的故事」 |
| `story_approved`（P/VP 核可） | **只有 Co-President** | `/admin/` 的「校友頁」分頁 |

兩個都是 true，那個人才會出現在對外的 `/alumni/` 上。
只有本人打勾的話，一個高一的幹部可以自己把自己放上去，而 CLAUDE.md 的紅線是
「未成年一律不放」；只有 P/VP 核可的話，就變成別人替他決定要不要公開自己的故事。
`story_approved` 不是本人改得動的欄位，前端沒有那條路，只能走資料庫的
`set_story_approved()`，而那支函式只有 Co-President 叫得動。

### 怎麼發一組校友碼

發碼的步驟跟上面「怎麼發新邀請碼」那一節完全一樣，**只是多填一欄**：

- 在 `invite_codes` 那一列多填一欄 `grants`，值填 `alumni`（不填的話預設是 `cadre`，
  也就是幹部碼，行為跟現在一模一樣）
- `grants` 只能是 `cadre` 或 `alumni` 兩種值，資料庫用 check constraint 擋著，
  打錯字會直接被拒絕，不會安靜地變成別的東西

一組碼用掉之後，那個人的身分（`cadre` 還是 `alumni`）由**那組碼**決定，
不是由使用者自己選 —— 系統裡沒有任何一個地方讓人自己勾「我要當校友」，
理由是身分本身是權限的一部分，讓人自己選一定有選錯的人，而選錯是權限問題。
校友沒有護照，用校友碼註冊**不會**在 `passports` 建一列。
其餘規則（大小寫不算數、失敗的註冊不消耗邀請碼）跟幹部碼完全一樣，見上面那一節。

### 核可前要確認的三件事

`/admin/` 的「校友頁」分頁上，核可前面就印著這三件事，資料庫不會替你檢查，
點下去之前自己想一遍：

1. **他滿 18 歲了嗎。** 未滿一律不放，不管職位。系統沒有生日欄位存不了這件事，
   所以這一條**只有核可的人擋得住**。
2. **他真的是 BT 校友（或幹部）嗎。** 邀請碼有可能被轉手給別人。
3. **這段文字現在這樣公開沒問題嗎。** 核可核的是「當下這一版」文字，
   他核可之後再改那句話或介紹，系統會自動把核可打掉，見下面那一段。

### 改了文字會自動下架，而且這件事寫在資料庫裡

一個人被核可上去之後，如果又跑去改自己的「一句話」或「介紹」（中英文都算），
資料庫的 trigger 會自動把 `story_approved` 設回 `false`，那個人立刻從
`/alumni/` 上消失，要 Co-President 重新核可一次才會再出現。**改城市、改學校
不會觸發**——那是事實更新，不是換一段用 BT 名義公開的話。

寫在資料庫裡（用 trigger），不是寫在某個前端頁面的程式碼裡，理由是**這樣才擋得住
所有路徑**。校友或幹部改故事可能是從 `/settings/` 改，也可能以後多一個地方能改，
如果「改了要重審」這條規則寫在某一個頁面的 JavaScript 裡，只要有第二條路能碰到
那張表，這條規則就形同虛設。寫在資料庫的 trigger 上，不管從哪裡改，這條規則
永遠生效，因為 Postgres 自己會執行它，不需要每個呼叫的地方都記得檢查一次。

### `/alumni/` 的資料來源順序

這一頁**先問資料庫，一個人都撈不到才退回示範資料**（`community.json`），
不是反過來。原因記在 `~/Anson/decisions/log.md` 2026-09-11 那一筆：這推翻了
2026-09-07 原本「`/alumni/` 不接資料庫、資料只走 `community.json`」的決定，
因為真名單一直上不去，卡點正是「要 Paul 一個一個收資料跟同意」。改成本人

技術上這一頁仍然**不載入完整的 supabase-js 套件**（對外頁面刻意不碰帳號登入

## 官網首頁的照片：可以放的依據是什麼

## 時間看板怎麼用（給幹部與管理者）

**每個人填自己「每週固定有空」的時段，不是特定日期。**
所以更新頻率是一學期一兩次，不是每場會議一次。要約會議的時候直接看看板挑，
在群組說一句「請大家更新一下自己的時間」就好。

第一次進去會有兩道關卡：一段告知（見下一節），然後設定自己的所在地。

### 填的方法：用批次，不要一格一格點

「我的時間」上面那一塊才是主要的填法：選時段（例如 19:00 到 22:00）、
勾要套用的星期（有「平日」「週末」「全部」快捷）、按「加入這段」。
還可以把某一天整天複製到別的幾天。

底下的格線是給微調用的。**在手機上一格一格點一百下等於沒做**，
批次那一塊就是為了這件事存在的。

「到 22:00」**不包含** 22:00 那一格 —— 講「到 22:00」的意思是那時候就結束了。

### 該催誰：看「成員」那一頁

那一頁列出**所有幹部**，包含從沒填過、以及還沒設定時區的人。
超過 30 天沒更新的整列會有底色，並且寫著「該更新了」。

- **「還沒填過」** —— 他從來沒有填過。看板上完全沒有他。
- **「還沒設定時區」** —— 他填的時間**畫不出來**，所以不會出現在團隊看板上。
  那不是他沒空，是我們不知道該把他畫在哪裡。這一種最容易被漏掉，
  因為看板看起來是完整的。
- **「我確認過了，沒有變」** —— 作息沒變的人按這顆就好，不必重填。
  那個 30 天要問的是「這份資料還可信嗎」，不是「他最近有沒有動過」。

### 有人說看板是空的

看板自己會講是哪一種空：沒有人設時區、沒有人填過、或者這一週對不上。
先看那句話再查別的。

**如果他說「我填了但看板上看不到」**，依序問：

1. 他有沒有按儲存（按鈕會從「儲存」變成「已儲存」）
2. 他的時區設了沒（成員那一頁看得出來）
3. 看板是不是捲到別的時間去了 —— 完整 24 小時都在，往上下捲得到

### 一個人的資料壞掉不會拖垮整頁

沒設時區的人只有他自己畫不出來，其他人照樣正常。有測試守著這件事，
因為「一筆壞資料拖垮整頁」是很容易寫出來的形狀，而真的發生的時候，
三十個人會同時看不到看板。

## 時間看板跟護照的保護等級不一樣

**護照的心得與照片是「只有本人看得到」。時間看板不是。**

看板要回答的就是「這一格有誰有空」，而時區換算必須在觀看者的瀏覽器裡做
（每個人的時區不同，夏令時間各自切換）。所以**每個幹部的瀏覽器都會拿到
全部人的完整作息表**——不是人數統計，是每個人每一格的原始資料。

這是功能本身的形狀，不是可以修掉的東西。RLS 把它限制在 `role = 'cadre'`，
未登入的人與學員一列都讀不到，但**幹部之間它是全開的**。
一個幹部想把全部人的作息表存下來，打開瀏覽器的開發者工具就有了，
這條路關不掉。

要記得的三件事：

1. **兩種資料在同一個網站、同一個帳號底下，而使用者不會自動知道差別。**
   所以看板第一次進去會明講「你填的每週時間，其他 BT 幹部看得到」，
   那句話是這個功能唯一的知情同意，不是禮貌用語
2. 那是三十個人的**長期作息表**——哪一天誰固定不在、誰每個週末都有空。
   幹部裡有未成年成員，這比一次性的投票敏感得多
3. **不要為了方便把看板開放給學員或做成公開連結。** 讀取政策是
   `is_cadre()`，改動它之前先回頭讀這一節

（規格 §4-5 有同一件事的完整版。這裡不重複細節，只放結論與那條界線。）

## 為什麼金鑰可以放在原始碼裡

有人看到 `shared/supabase.js` 裡有一長串金鑰會嚇一跳，以為外洩了。沒有。
（2026-08-31 之前這一份在 `src/config.js`，階段 2 併進 `shared/supabase.js`。）

那個是 **publishable key**（`sb_publishable_` 開頭），它就是設計成公開的，
任何打開網頁的人都拿得到，這是正常的。它只能做「已登入的人可以做的事」，
真正擋住別人看你心得的是資料庫裡的 RLS 規則，不是這把金鑰。

**但是** —— 另外有一種 **secret key**（`sb_secret_` 開頭），
那把會繞過所有規則，拿到就等於拿到全部人的心得和照片。

- 絕對不要把 secret key 放進程式碼、放進 GitHub、貼進群組、或截圖露出來
- 這個專案完全不需要 secret key
- 如果哪天覺得「好像要用 secret key 才做得到」，那是規則寫錯了，去修規則

### 不要照著錯誤訊息裡的「hint」做

資料庫拒絕存取時，回來的訊息常常附一個 `hint` 欄位，直接告訴你怎麼把限制解除。例如：

> `permission denied for table invite_codes`
> hint: `Grant the required privileges to the current role with: GRANT SELECT ON public.invite_codes TO authenticated;`

**那句 hint 不要照做。** 它是資料庫在機械式地告訴你「怎麼讓這個錯誤消失」，
不是在建議你該怎麼做。`invite_codes` 讀不到就是我們刻意設計的 ——
照著做等於把全部邀請碼公開給每一個登入的人。

遇到 `permission denied`，正確的反應是問「為什麼這裡會需要讀這張表」，
不是把權限開下去。

## 不要刪活動

某一格不辦了，**不要刪除那一列**。已經有人蓋過章的話，刪掉會連他的章
和心得一起弄壞。

正確做法：Table Editor → `activities` → 那一列的 `active` 改成 `false`。
它就不會再出現在護照上，但已經蓋過的人資料還在。

## `destinations`（城市池子）可以怎麼動

> **加新城市的話，時區別名表也要跟著加。**（2026-09-02）
> 時間看板要靠 `availability/src/tz-alias.js` 把城市名對到 IANA 時區
> （幹部不知道自己在 `America/Detroit` 還是 `America/New_York`，小城市尤其猜不到）。
> `test/tz-alias.test.mjs` 有一條在守那 24 個城市都搜得到，少一個就紅。
>
> **但那條測試讀的是 `supabase/migrations/2026-08-26-destinations.sql`，不是資料庫。**
> 所以直接在後台的 Table Editor 加城市的話，測試看不到那個改動，會繼續全綠 ——
> 而那個城市的幹部設定時區時會搜不到自己在哪裡。
> 在後台加城市時，請一併：(1) 補一份 migration 記下這次改動，(2) 在別名表加對應的中英文名。


**加城市是安全的**，而且會常常發生 —— 每年都有人搬家、交換、畢業，
不是哪天可能，是一定會遇到。為什麼安全：一個月份蓋滿的當下，抽到的城市就存進
`visas`，之後池子再怎麼變，已經存下來的那些不受影響。

**刪城市的話資料庫會擋。** `visas.code` 對 `destinations(code)` 有外鍵，
只要有人蓋過那個城市，`delete` 就會失敗。這是約束，不是規則 ——
不需要有人記得「不要刪」，資料庫自己會擋。

**停用是可以的**：Table Editor → `destinations` → 那一列的 `active` 改成 `false`。
新的抽籤不會再抽到它，但已經發出去的入境章照樣顯示
（`visasOf` 查表用完整池子，只有抽籤才過濾 `active`，見它自己的註解）。

**這一整段的前提是「城市在蓋滿的當下存進 `visas`，而 `visas` 沒有 update 權限」。**
哪天有人給那張表開了 update，這一段就不再成立。

## Supabase 的 SQL Editor 有兩個要先知道的限制

第一次貼 SQL 進去的人一定會踩到這兩件事，先講：

**1. 它只顯示「最後一句」的結果。** 一份腳本裡有十句，前面九句的輸出你都看不到。
所以 `supabase/rls-test.sql` 的最後一句是一個 `select`，把檢查結果整理成一張表 ——
不是因為那樣比較好看，是因為不那樣做你就什麼都看不到。

**2. 它不顯示 `raise notice`。** PostgreSQL 的 `notice` 走的是另一條訊息通道，
SQL Editor 不會呈現。**不要叫人去找 notice 訊息，那裡永遠是空的。**
腳本跑完只看到「Success. No rows returned」不代表成功，只代表最後一句沒有回傳資料。

所以判斷 `rls-test.sql` 有沒有過，看的是那張表的第一列 `OVERALL 全部測試`：

- `PASS` → 全部通過
- `FAIL` → 往下看，失敗的列會被排在最上面，`expected` 與 `actual` 兩欄會告訴你差在哪

## 要改資料表結構的話

`supabase/schema.sql` 的檔頭寫著「可以重複執行」，那句話只保證**重跑不會弄壞資料**。

它**不保證會更新結構**。`create table if not exists` 遇到已經存在的表就整個跳過，
不會比對欄位、不會補欄位、也不會報錯 —— 你會以為改好了，其實資料庫還是舊的。

所以：**資料庫已經有真實資料之後，要改欄位、改型別、改約束，一律另外寫一段
`alter table …` 執行，不要改 `schema.sql` 再重跑。** 改完之後也把 `schema.sql`
一起更新，讓它對新專案仍然正確。已經有一個例子可以照抄：`supabase/migrations/`。

（`create policy` 與 `create or replace function` 那些是會更新的 —— 它們寫了
`drop policy if exists` 與 `or replace`。會靜默跳過的只有「表和欄位」。）

## 管理者怎麼處理帳號問題

### 先講規矩

你在 Supabase 後台看得到所有人的心得和照片。這是後台權限的必然，
**不是你可以看的意思。**

- **不因為好奇去翻別人的心得。** 只有在對方主動求助時才進去，而且要先告訴他
- **不要幫人設密碼。** 2026-09-02 起網站上有自助重設，走那條路你不會知道他的密碼，
  他也不必信任你保管它。你在後台設一組密碼給他，等於你們兩個人都知道那組密碼，
  而他多半不會去改掉
- 不要把後台截圖貼進群組 —— 截圖常常連金鑰一起入鏡

護照裡有未成年幹部寫的東西。他們是相信這件事才寫的。

### 逐項處理

> **這一節 2026-09-02 改寫過。** 舊版是寫給「管理員幫你重設密碼」那個世界的，
> 而網站現在有自助重設了；還有幾段指到已經不存在的資料表。
> 舊版沒有寫錯，是它的前提換掉了（第 11 項）。

**「我忘記密碼了」**

**請他自己弄，你不要進後台。** 護照登入頁 → 「忘記密碼？」→
「寄一封重設連結給我」→ 打 email → 收信 → 點連結 → 設新密碼 → 直接登入。

你要做的只有兩件事：確認他知道自己當初用哪個 email，以及等他回報。

**你在後台幫他設密碼是最後手段，不是第一步。** 那條路的代價是你們兩個人都知道
他的密碼，而他多半不會回頭去改掉。真的走到那一步（他連 email 都沒了、
信箱進不去），設完立刻私訊給他、請他登入後馬上自己改一次，
然後把那組密碼從你的對話紀錄和筆記裡刪掉。

**「我按了忘記密碼，但沒收到信」**

依序排除：

1. **垃圾郵件匣。** 最常見。信是從 `noreply@beyondtaiwannpo.com` 寄的
2. **email 打錯了。** 那一頁不會告訴他「這個信箱沒有帳號」——
   這是刻意的（不然任何人都能拿它一次一個 email 問「這個人是不是 BT 幹部」），
   代價就是打錯字的時候畫面看起來一切正常。請他再打一次，看清楚
3. **他其實是用 Google 登入的。** 那種帳號沒有密碼，見下一項
4. **連按了好幾次。** 畫面會說「等一分鐘再按一次」，那是真的，不是敷衍
5. 以上都不是 → Resend 後台看寄送紀錄（Emails），那裡看得到有沒有寄出、
   有沒有被退回

**「它說我還不是 BT 幹部」**

這是**正常的**，不是壞掉。2026-09-01 起註冊出來的每個人預設都是學員，
在畫面上輸入邀請碼才會升級成幹部。那一頁本身就有輸入框，請他在那裡輸入。

那一頁還有一件事要他知道：升級之後他的名字和團隊會出現在進度牆上，
其他幹部看得到。頁面上寫著，但值得你再講一次。

輸入之後說「這個邀請碼不對，或是已經被用完了」→ 就是那組碼真的不能用
（不存在，或次數用完了），見「怎麼發新邀請碼」。
**這句話 2026-09-01 起是可信的**，以前它同時涵蓋伺服器出狀況，現在不會了。

**「我用 Google 登入，要密碼嗎」**

不用。Google 登入的帳號沒有密碼，他每次都按那顆 Google 按鈕就好。

他如果已經按過忘記密碼、也真的設了一組密碼，那不會壞掉 ——
那個帳號從此兩種方式都能登入。

**「我 email 打錯了／要換 email」**

Authentication → Users → 改 email。
章和心得是綁在帳號上的，換 email 不影響，資料不會不見。

**護照裡沒有讓使用者自己換 email 的地方**，所以這件事目前只能由你做。
（`supabase/email-templates/change-email.html` 那份範本是先寫好放著的，
等哪天做了自助換信箱才會用到。你在後台直接改不會寄出那封信。）

**「我不屬於任何一組，團隊要選什麼」**

會問這句的通常是 President 或 Vice President —— 他們跟每一組都有關，不屬於其中任何一組。

**請他選自己原本出身的那一組。** 一進來就是 P/VP、沒有出身組的話，
選最常一起做事的那一組。

要讓頭銜看得見的話，寫在「護照上的一句話」那一欄（自由文字，印在資料頁上），
例如「President 2026-27」。

**不要為了他們在團隊清單裡加一個選項。** 那個清單只放團隊、不放職位 ——
一旦混進一個職位，下一個問題馬上會來：秘書呢？顧問呢？同時在兩個組的人呢？
而那一欄顯示在進度牆上，它要回答的是「這個人跟哪一組做事」，不是「他的頭銜是什麼」。
（`passport/src/ui.js` 最上面的 `TEAMS` 那段註解寫了同一件事，改之前先讀。）

**「我想改姓名／團隊／護照上那句話」**

請他自己在護照的資料頁按「編輯資料」改。

真的改不動才由你進 Table Editor，而**這三樣不在同一張表**
（階段 3+4 拆開的，2026-09-01）：

| 他想改的東西 | 在哪張表 | 欄位 |
| --- | --- | --- |
| 中文名 / 英文名 | `profiles` | `name_zh` / `name_en` |
| 團隊 | `profiles` | `team` |
| 護照上的一句話 | `passports` | `motto` |

找不到欄位的時候先確認自己開的是哪一張表 —— 兩張表的主鍵都是同一個
使用者 id，長得很像。

**「我要一組邀請碼」**

看上面「怎麼發新邀請碼」。

**「我不小心註冊了兩個帳號」**

1. 先確認哪一個有章（Table Editor → `stamps`，看 `user_id`）
2. **再確認哪一個是幹部**（Table Editor → `profiles`，看 `role`）。
   有章的那個通常就是幹部那個，但不保證 —— 他可能先升級了 A 帳號、
   後來又用 B 帳號在活動裡蓋章
3. 刪掉沒有章、也不是幹部的那個：Authentication → Users → 該列 `⋯` → Delete user
4. 章和心得會跟著一起清掉，這是設計好的

> **兩個都是幹部的話，他用掉了兩組邀請碼**，而刪掉帳號**不會把次數還回來**。
> 直接去 Table Editor → `invite_codes` 把那組碼的 `uses_left` 加回 1，
> 並在 `note` 寫清楚為什麼（例如「2026-09-02 重複註冊，人工還原一次」）。
> 不寫的話下次盤點會對不起來，而且沒有人知道是誰動的。

**「我要離開 BT，請刪掉我的資料」**

> **順序不能反。刪帳號的那一刻，他的章、心得、照片全部一起消失，救不回來。**
>
> 資料表是 `on delete cascade` 設計的：刪掉 `auth.users` 那一列，`profiles`、
> `passports`、`stamps`、`entries`、`visas` 裡屬於他的每一列都會被連帶刪除
> （2026-09-02 對著資料庫的外鍵定義查證過，不是照記憶寫的）。這是刻意的（他要求刪資料，
> 就該刪乾淨），但也表示**先刪帳號再想到要備份就來不及了**。免費方案沒有自動備份，
> 資料庫裡也不會留副本。

1. **先請他自己匯出。** 護照資料頁 → 「匯出備份」→ 下載 JSON 檔。
   **等他回報「檔案拿到了」再往下做。** 不要你幫他匯出，也不要跳過這步
2. 他說不需要備份的話，跟他確認一次：「刪掉之後這一年的章和心得都回不來，確定嗎？」
3. 確認之後：Authentication → Users → 該列 `⋯` → Delete user
4. 刪完不要再問「要不要復原」—— 沒有復原這個選項

**「我的章不見了」**

1. 先問他是不是登錯帳號 —— 這是最常見的原因，尤其是註冊過兩次的人
2. **先問他畫面長什麼樣，這一句分得開兩種完全不同的原因：**
   - 畫面說「你還不是 BT 幹部」→ 他的 `role` 不是 `cadre`，章沒有不見，
     是他讀不到。請他輸入邀請碼升級
   - 畫面是護照的樣子，但**一個活動格子都沒有** → 這比較嚴重：
     多半是 `profiles` 裡根本查不到他那一列。去 Table Editor → `profiles`
