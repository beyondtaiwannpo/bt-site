# 後台重整：盤點與設計提案

2026-10-15。給 Paul 看的。這一輪沒有動任何程式，等你拍板再動。

起因是你說的：「現在很多東西都在申請管理裡面，可以根據內容重新排一次嗎？我要原本的護照活動 Co-President 也都可以改，然後設計 BT 內部權限等等都要在裡面，它要是一個完整的 Dashboard 後台，可以管理前站等等。」

這份文件分三段：第一段講 `/admin/` 現在有什麼、缺什麼；第二段給兩個重排的做法比較加一個建議；第三段是我自己當審查者讀三輪的紀錄，每一輪抓到的問題都已經修回設計裡。
開頭先放一定要你決定的事，因為它們會改變做法。

幾個會一直出現的詞，先講一次：

- **RLS**（Row Level Security）：資料庫層的規則，決定誰看得到、動得了哪幾列。前端程式改不掉它。
- **security definer 函式**：資料庫裡的一支小程式，用資料庫管理員的身分跑，所以它可以做一般使用者做不到的事。我們的規矩是每一支的第一句就是守門，例如 `is_president()`。
- **`role`**：這個人是誰。`cadre` 幹部、`student` 學員、`alumni` 校友、`intern` 實習生。只有拿邀請碼才會變。
- **`board_role`**：幹部裡管到哪。`member` 一般幹部、`director` 某個 team 的 Director、`president` 當屆 Co-President。
- **遷移檔**：改資料庫結構或權限的 SQL 腳本，放在 `supabase/migrations/`，要貼進 Supabase 跑一次。

1. **「管理前站」是哪一種？** 兩種解讀，我建議 a。

3. **改權限要不要兩位 Co-President 都點頭？** 三個選項：甲 一位就能改，但每一筆改動留紀錄，兩位都看得到；乙 一位提、另一位按確認才生效；丙 維持現狀（只能下 SQL）。我建議甲。理由在 2-4。

5. **後台要不要拆資料夾？** 2-2 的方案乙會把 `/admin/` 拆成四個資料夾。這是結構決定，影響的是明年接手的人在哪裡找東西。我建議拆。
6. **這一季做到哪？** 2-6 排了四批。我建議這一季做前兩批（重排加護照活動、人與權限），後兩批（名單匯出、其餘）看時間。另外 GOALS.md 目標 2「交接實測」死線是 2026-10-31，還沒做，這件事不該排在它前面。

## 1. 盤點

### 1-1. `/admin/` 現在有什麼

程式在 `admin/` 一個資料夾：`index.html` 加 `src/data.js`（唯一碰資料庫）、`src/ui.js`（畫畫面）、`src/main.js`（接點擊）。分頁列是 `ui.js` 的 `tabsHTML()` 畫的，依 `board_role` 決定顯示幾個。
頂欄上這一頁叫「申請管理」，所有幹部都看得到入口。

| 分頁 | 給誰用 | 資料在哪張表 | 看還是改 | 門在哪 |

九件事擠在一條分頁列上，而且名字叫「申請管理」的頁面裡有六件事跟申請無關。這就是你說的「很多東西都在申請管理裡面」。

### 1-2. 不在後台、但你要的

#### 護照活動（幹部護照的格子）

#### BT 內部權限

## 2. 設計

### 2-1. 新的分組

不管選哪個方案，分組都是這五組。「看」是這一組的人看得到，「改」是按得動。

| 組 | 裡面有什麼 | 誰看得到 | 誰改得動 |
|---|---|---|---|
| **申請** | 申請表、收到的申請、審核三顆按鈕、簽到、行前信、待寄的信總覽 | 所有幹部（自己 team 的） | Director 自己 team 的；Co-President 全部 |
| **對外** | 團隊頁核可、校友頁核可、資源目錄、信件文案 | 資源：所有幹部；其他三項：Co-President | 資源：Director 自己 team 的；其他三項：Co-President |
| **護照** | 幹部護照的格子（活動、月份、城市）、實習護照的格子與屆別 | 幹部護照：Co-President；實習護照：Internship Team 與 Co-President | 同左 |
| **人與權限** | 幹部名單（名字、team、職位、進來的日期）、改職位、改 team、權限變動紀錄、邀請碼 | Co-President | Co-President |
| **設定** | 名單匯出（電子報）、系統狀態（遷移檔跑到哪一支、寄信還通不通） | Co-President | Co-President |

「設定」那一組這一季只放名單匯出，系統狀態是以後的事，先占一個位置。

### 2-2. 兩個方案

**方案甲：留在一個資料夾，分頁列分組。**

`admin/` 不拆，`tabsHTML()` 改成兩層：上面一排是五個組，下面一排是那一組裡的分頁。新功能照舊加進 `data.js`、`ui.js`、`main.js`。

- 好處：改動最小，一批就能做完重排。網址不變，README 不用大改。
- 壞處：`ui.js` 現在 881 行、`main.js` 703 行，加上護照活動與人與權限大概會到 1,500 與 1,100 行。三支檔案裡放五件不相干的事，明年接手的人要改「資源的說明文字」得在一千多行裡找。而且一個檔案壞掉全部一起壞：護照活動編輯器裡一個錯字，申請審核頁也打不開。這跟「一個功能壞掉不該讓別的功能打不開」那條規矩相反。

**方案乙：拆成四個資料夾，`/admin/` 當後台首頁。**

```
admin/              後台首頁加「申請」那一組（最常用，所有幹部都用）
admin/site/         對外：團隊頁、校友頁、資源、信件文案
admin/passports/    護照：幹部護照的格子、實習護照的格子
admin/people/       人與權限：幹部名單、職位、team、變動紀錄、邀請碼、名單匯出
```

每個資料夾一個 `index.html` 加自己的三支 js，各自讀 `shared/` 的那三個共用檔，**資料夾之間不互相 import**（跟 `passport/`、`availability/`、`intern-passport/` 同一條規矩，`check.sh` 已經在守）。`/admin/` 最上面放一排入口卡片：這一組是做什麼的、你有沒有權限進去，沒權限的卡片灰掉並寫一句「這一組只有 Co-President 用得到」。

- 好處：符合「開一個資料夾、放一個 HTML、讀那三個共用檔案」。每個資料夾兩三百行，一眼看得完。一組壞掉不影響其他組。權限也跟著資料夾走：`admin/people/` 開頁第一句就檢查 `board_role`，不是的人整頁只看到一句話。
- 壞處：`esc()`、`namesOf()` 這類小工具會多出幾份複本（repo 已經有三份，`test/names.test.mjs` 在守一致性，新的照樣加進去）。網址會變，README 裡講到「邀請碼分頁」的段落要改路徑。頂欄 `shared/nav.js` 那一筆要從「申請管理」改名成「後台」並指向 `/admin/`，子資料夾不進頂欄（`nav.js` 檔頭禁止在那裡加 `board_role` 過濾，所以子資料夾由首頁的卡片帶，不由頂欄帶）。

### 2-3. 建議：方案乙

理由只有一個：北極星看的是交接得動不動，不是這一批做得快不快。方案甲省下的是這一次的半天，方案乙省下的是明年每一次「這段在哪」。

而且方案乙的第一批其實很機械：把既有的分頁原樣搬進對的資料夾，不改行為，測試跟著搬。搬完再加新東西。

### 2-4. 三個風險怎麼擋

#### 風險一：改護照活動改壞已經蓋好的章

護照活動的後台照實習護照那一套做，那一套已經在正式站跑過：

- **編號在畫面上不是輸入框，是標籤。** 新增一格時由系統照月份與分類算出來（`09A`、`09B`、`09C` 那個規則），不讓人打。
- **已經有人蓋過的格子，「刪」那顆按鈕不出現，只有「停用」。** 資料庫那一支函式也擋：有章就拒絕刪。兩層都有，畫面少一顆按鈕不是安全機制。
- **城市只有「加一個」與「停用」，沒有「刪」。** 資料庫本來就擋（`visas` 的外鍵），後台不給那顆按鈕，免得按了看到一行英文錯誤。
- **月份只開放改右上角那個時刻字串**，`seq` 與 `month` 不出現在畫面上。
- 每一支寫入函式第一句 `is_president()`。表本身對前端維持只有讀的權限。
- 這一組**完全不碰** `stamps`、`entries`、`visas`、`passports`。GOALS.md「不動 `/passport/` 的隱私界線」那條不受影響：後台看得到每一格被蓋過幾次（數字），看不到誰、更看不到心得。

#### 風險二：改內部權限改出一個不該有的 Co-President

三件事分開看：

**`board_role`。** 走既有的 `set_board_role()`，它已經擋了三件事：不是 president 不能叫、不能把自己降級、只能發給幹部。這次加兩件：

- **每一筆改動寫進一張新表 `role_changes`**：誰改的、改誰、從什麼到什麼、什麼時候。只有 Co-President 讀得到（RLS `is_president()`）。「人與權限」頁最上面就是這張紀錄的最近十筆，兩位 Co-President 一登入就看得到對方動過什麼。這不是通知，不寄信，不違反「不做站內通知中心」；它是帳本。
- **把人升成 president 時，畫面多問一次**，寫清楚「他會拿到跟你一樣的全部權限，包括把你降級」。資料庫那一側不加限制，因為換屆就是要把新的人升上來、再把自己降下去。

要不要兩位都點頭（第 0 段第 3 題），我建議不要。三十個人的組織，雙人核可的代價是「另一位在國外睡覺，這件事等十二小時」，而它要擋的事（一位 Co-President 偷偷升一個人）有紀錄就擋得住，因為另一位看得到。真要防的是帳號被盜，那不是這一層該擋的。

**`team`。** 這是這次抓到的洞，要先補，不然護照活動與實習護照的權限都站不穩：

- 現狀：任何幹部在 `/settings/` 把自己勾進 Internship Team，就能改實習護照的格子；Director 勾到別的 team 就能審那個 team 的申請、改那個 team 的資源。
- 建議：加一條資料庫 trigger（存檔前自動跑的檢查）：**`board_role` 是 `director` 或 `president` 的人，`team` 只能由 Co-President 改**；一般幹部仍然自己勾，但**勾進會長出權限的 team**（現在只有 Internship Team，之後 Curriculum Team 若接護照活動也算）要 Co-President 改。「會長出權限的 team」列在一張小表裡，不寫死在程式。
- `/settings/` 的 team 那一塊對這些人變成唯讀，旁邊寫「你的 team 由 Co-President 設定，要改請找他們」。
- 這會動到 RLS 與既有資料的行為，所以是「停下來問 Paul」那一類。

**`role`。** 建議後台這一季**不做** `role` 的改動。它只走邀請碼有一個好處：每一次身分變動都有一筆 `invite_uses` 紀錄對得回去是誰發的碼。換屆把幹部轉成校友這件事（這一屆 2027-07 才會遇到）等遇到再設計，到時要連護照怎麼封存一起想。

#### 風險三：「管理前站」變成內容管理系統

照第 0 段第 1 題的 a 做：「對外」那一組只放資料庫裡本來就有的東西。後台首頁那張卡片上寫明「對外七頁的文字在 HTML 裡，改法見 README」，讓明年的人不會在後台找文案編輯器找不到。

### 2-5. 北極星檢查

- **`shared/` 不變大。** 這次只改 `shared/nav.js` 裡那一筆的名字與說明（「申請管理」改「後台」），不加檔案，不加 `board_role` 過濾。
- **不加框架、不加 build step。** 四個資料夾都是原生 JS，跟現在一樣。
- **資料夾之間不互相依賴。** `admin/site/` 不 import `admin/src/`。`check.sh` 那段依賴守門要把新資料夾加進去。
- **每一支新函式都有 PASS / FAIL 驗收表**，跟既有遷移檔同一個樣子，而且要有一條破壞測試：拿掉第一句的門，看對應那幾條變紅。
- **README 跟著改。** 「怎麼改活動文案」那一節從「去 Table Editor」改成「去後台的護照那一組」，Table Editor 那條留著當備用。

### 2-6. 分批與優先序

| 批 | 做什麼 | 要不要遷移檔 | 建議時程 |
|---|---|---|---|
| 1 | **重排**：拆成四個資料夾，既有九個分頁原樣搬進去，`/admin/` 變首頁加申請。頂欄那一筆改名。待寄的信總覽順手做。README 路徑更新 | 不用 | 拍板後第一件 |
| 2 | **護照活動**：`admin/passports/` 加幹部護照的格子、月份時刻、城市。一支遷移檔開寫入函式 | 要，一支 | 批 1 之後 |
| 3 | **人與權限**：幹部名單、改職位（接既有 `set_board_role()`）、`role_changes` 紀錄表、team 的守門 trigger、`/settings/` 的 team 唯讀。邀請碼分頁搬過來 | 要，一到兩支 | 第 0 段第 2、3 題拍板之後 |
| 4 | **名單匯出**：`admin/people/` 多一顆按鈕，下載同意收電子報的名單（CSV） | 要，一支只讀函式，門 `is_president()` | 看時間，2027-01 嘖嘖搶先看之前要有 |

這一季（到 2026-12-31）建議做批 1、2、3。批 4 排在嘖嘖前。
批 3 動到權限與 RLS，照 GOALS.md 的優先序它自動升到第 1、2 級，所以**批 3 不該因為趕時間而簡化掉紀錄表或 trigger**。

GOALS.md 目標 2「一位沒寫過程式的幹部照 README 自己改一次首頁文案並上線」死線 10-31，還沒做。那是這一季唯一真正重要的一項。這份後台重整不該排在它前面；如果兩件事搶同一個星期，先做目標 2。

## 3. Loop 自我檢測

設計寫完之後，我當審查者從頭讀三輪，每一輪換一種眼睛。抓到的問題都已經修回上面的設計，這裡記錄改了什麼。

### 第一輪：一位沒寫過程式的下一屆幹部看不看得懂、接不接得手

抓到四件，都修了：

1. 文件一開始就在用 RLS、security definer、`board_role` 這些詞。**修法**：開頭加一段詞彙表，每個詞一句話。
2. 資料夾名字 `site`、`passports`、`people` 是英文，接手的人不一定對得上「對外」「護照」「人與權限」。**修法**：2-2 的資料夾樹每一行後面寫中文用途；批 1 要在 README 加一張「我要改什麼，去哪個資料夾」的對照表；後台首頁每張卡片用中文寫這一組是做什麼的。
3. 「人與權限」頁上如果直接寫 `board_role`、`member`、`director`，幹部看不懂。**修法**：畫面上一律叫「職位」，三個值顯示成「一般幹部」「Director」「Co-President」，`board_role` 這個字只留在程式與文件裡。
4. 後台首頁沒有說「對外文案不在這裡」，明年的人會在後台找文案編輯器。**修法**：2-4 風險三那一句加進首頁卡片。

### 第二輪：安全，有沒有任何一項讓非 Co-President 改到別人的資料或權限

抓到三件，兩件修了，一件變成第 0 段的題目：

1. **`team` 由本人自改，但權限看它。** 這一條在第一版設計裡沒有，是這一輪讀 `is_director_of()` 與 `is_internship_team()` 的定義時發現的。它現在就存在，不是重整之後才有。**修法**：2-4 風險二加 trigger 與 `/settings/` 唯讀，列為第 0 段第 2 題。連帶把第 4 題「護照活動要不要開給 team」的建議改成「先只給 Co-President」，不然等於把同一個洞再開一次。
2. 第一版設計寫「`role_changes` 紀錄表所有幹部看得到，讓改動透明」。這會讓一般幹部看到「誰被降級」，那是人事資訊。**修法**：只有 Co-President 讀得到，RLS `is_president()`。
3. 護照活動的讀取：後台頁面讀 `stamps` 算「每一格被蓋過幾次」。`stamps` 本來就是幹部之間公開的（進度牆），所以 Co-President 讀它沒有多看到什麼。但設計裡要寫死**不讀 `entries`**，而且查詢只拿 `act_id` 不拿 `user_id`，跟實習護照那一支 `loadInternAdmin()` 同一個做法。**修法**：寫進 2-4 風險一最後一點。

另外確認過沒有問題的：`set_board_role()` 只對 `role = 'cadre'` 的人生效，所以不會出現「學員被升成 president」；`set_board_role()` 擋自我降級，所以永遠至少留一位 president；所有 Co-President 專用的讀取（校友故事、邀請碼紀錄）都走函式不走表，新加的也照這樣。

### 第三輪：對照 GOALS.md 每一條「明確不做」與「停下來問 Paul」
