# 行銷需求單（2026-10-24 設計）

Paul 2026-10-24：「其他 team 要跟 Marketing 提需求，要有一張表單，送出去給 Marketing team。」
已經跟 Paul 定好的：任何幹部都能送；新單進來寄一封信給 Marketing 需求工作區裡每一個「管」的人；標成「做完了」寄一封信給送單的人；做完的單留著（用篩選看），不自動封存。
**申請表那套引擎（forms / applications）是給外面的學生用的，不拿來做這個。** 這是一張新的小表加一個新的工作區。

## 還要 Paul 決定的三題（其他都照下面做）

1. **信什麼時候寄出去。** 現在平台的信（錄取、面試、邀請）都是先排進 `mail_outbox`，等有人在總覽按「寄出」才送到 Resend。
   建議：**送單那一刻就寄**。送單的函式排完信直接叫 `send_pending_mail(5)`（送單的人是幹部，門過得了），Marketing 的人幾秒內就收到；Resend 沒設好的話信留在 outbox，總覽那張「還有 N 封信沒寄」的卡會看到。做完那封也一樣，標「做完了」當下就寄。
   另一條路是跟現在一樣等人按「寄出」，比較一致，但需求單這種東西等一天才收到就失去意義。
2. **誰可以改狀態、寫回覆。** Paul 的原話是「管」的人。建議放寬到**「改」以上**：工作區裡「管」的意思是可以加人、移人，那是 Director 的事；處理需求單的通常是 Marketing 的 Associate，給他們「改」就能接單。只有「看」的人看得到全部單、不能動。
3. **送單的人能不能自己收回。** 建議可以：狀態還是「新的」就能收回（變成第四種狀態 `withdrawn`，不寄信、留著）；已經在做了就不能收回，去找 Marketing 講。不要的話狀態就只有三種。

## 資料

一張表 `requests`：

| 欄 | 是什麼 |
|---|---|
| `id` uuid | |
| `kind` | `poster`／`post`／`video`／`other`（海報、貼文、影片、其他） |
| `title` | 一句話 |
| `purpose` | 給哪個活動或要做什麼 |
| `needed_by` date | 什麼時候要 |
| `brief` text | 內容說明 |
| `asset_links` text[] | 素材連結（Drive、Canva），表單上一行一條 |
| `contact` | 聯絡方式（預設帶 email，可以改成 LINE） |
| `requester` uuid → profiles | 送單的人 |
| `status` | `new`／`in_progress`／`done`（第三題說要就多 `withdrawn`） |
| `reply` text | Marketing 的回覆 |
| `created_at`、`updated_at` | |

RLS：
- 送單的人讀自己的（`requester = auth.uid()`）。
- Marketing 需求工作區「看」以上讀全部（`can_view('custom:marketing-requests')`）。
- 「改」以上（第二題）update `status` 與 `reply`，別的欄不准改。
- 沒有人直接 insert，一律走 `submit_request()`（security definer，第一句 `is_cadre()`），它寫一列、排信、寄信。
- 標狀態走 `set_request_status(id, status, reply)`（第一句 `can_edit('custom:marketing-requests')`），變成 `done` 就排一封信給送單的人。
- 送單的人收回走 `withdraw_request(id)`（第三題）。

工作區：`custom:marketing-requests`，kind `custom`、`team = 'Marketing Team'`、擁有人是 Marketing 的 Director（找不到就 Co-President）。
遷移檔建好之後**把 `res:Marketing Team` 現在的成員照原等級抄一份進來**（Paul 定的：另開一個工作區才能另外派人，但先讓 Marketing 現在的人都在裡面）。
之後要加人減人在 People → Workspaces 的 Marketing 那一列多一格「需求單」，跟別的工作區一樣。

信：`mail_templates` 與 `mail_outbox` 的 kind 多 `request_new`、`request_done`；`mail_outbox` 多一欄 `request_id`。
兩封的預設文案種進去（Paul 改過的不會被蓋），在後台「信件文案」可以改，代換符號：`{requester}` 送單的人、`{title}` 標題、`{needed_by}` 日期、`{link}` 直達那一張單、`{reply}` 回覆（只有做完那封有）。
`request_new` 寄給工作區裡每一個「管」的人（Paul 定的），一人一封；`request_done` 寄給送單的人。
`mail_outbox` 的讀取政策要多一條：`request_id` 不是空的那幾封，Marketing 需求工作區「看」以上讀得到（不然總覽「沒寄出的信」只有 Co-President 看得到這幾封）。

## 畫面（五個面）

1. **側欄「跟 Marketing 提需求」**：每一位幹部都有（`who: "cadre"`），放在「申請」那一組底下。一頁兩塊：表單（種類、標題、給哪個活動、什麼時候要、說明、素材連結、聯絡方式；送出去就一條 toast）與「我送過的」清單（狀態、Marketing 的回覆、第三題的「收回」）。
2. **Marketing 的佇列頁**：People → Workspaces 的 Marketing 那一列多一格「需求單」，連到 `/admin/#requests`。只有工作區裡的人（與靠職級的兩級）進得去。清單照狀態分段（新的、進行中、做完的），可以篩種類與狀態、找標題；點一張開來看全部欄位，改狀態、寫回覆、「標做完了」（會寄信，先問一次）。
3. **總覽的卡**：Marketing 需求工作區「改」以上的人看到「Marketing 需求單等處理：N」；送過單的人看到「你的需求單『X』進行中」（最近一張還沒做完的）。
4. **People → Workspaces**：Marketing 那一列多一格、成員區跟別的工作區一樣（這一批不用改程式，`wsRows` 看 `team` 欄就會放對列）。
5. **信件文案**：兩種新的信可以改，有預覽。

## 不做

- 不做附件上傳，素材放 Drive 貼連結（跟 `/resources/` 同一條規矩）。
- 不做指派給某一個人、不做留言串；一張單一個回覆欄，要討論用 LINE。
- 不做站內通知；狀態變了就寄信（GOALS 的規矩）。
- 不做自動封存或刪除。
