# 時間看板：某一週的例外　設計　2026-09-12

Paul 2026-09-12：「之前說我的時間要可以填 specific 那一週的改過了嗎？
現在只有全部的時間，有成員反應要可以只填一週。」

沒有改過。而且不是設定沒開，是資料結構上還沒有「某一週」這個東西。

---

## 現在是什麼樣子

`availability` 那張表只有三欄：`user_id`、`weekday`（0 到 6）、`minute`（當地時間的
0 到 1439，半小時對齊）。**沒有日期。** 它存的是「我每週固定有空的時段」，
表的註解就是這樣寫的。

看板一次顯示一週，把每個人那份固定樣式照他自己的時區投影到你正在看的那一週上
（`availability/src/board.js` 的 `boardCounts()`）。所以你翻到哪一週，看到的都是同一份資料。

成員反映的是真實情況：大部分人的時間是固定的，但某一週會不一樣（考試週、出國、那週特別忙）。

---

## Paul 2026-09-12 拍板的六件事

1. **例外是「取代」不是「疊加」。** 某人為某一週填了例外，那一週就完全以例外為準，
   他平常的固定時段那一週不算。進去編輯時**預先帶出他平常的時段當起點**，
   他再把不行的拿掉、多出來的加上。這樣「這週我沒空」與「這週我多一個空檔」都接得住。
2. **本週加未來全部都可以填**，不限週數。**過去的週不能改** ——
   改已經過去的時間沒有意義，而且會讓人以為自己在改未來。
3. **看板往後翻不限，往前維持四週。** 能填多遠就要看得到多遠，兩邊對齊；
   往前只是回顧，而且本來就不能改。（原本前後各四週是 Paul 2026-09-02 定的，這次只放開往後那一邊。）
4. **只在他自己那一頁標示**哪幾週被特別設定過。看板上不分彼此 ——
   看板要回答的是「那一週誰有空」，不是「這筆資料怎麼來的」。
5. **資料放新的表**，現有那張「平常的時間」原封不動。
6. **要支援「這一週我完全沒空」**（有例外、但一格都沒勾）。

## 一、資料模型

兩張新表。**每一張都只有一句話講得完的職責**，這是為了換屆的人讀得懂。

```sql
-- 某一週的例外格子。形狀跟 availability 一模一樣，多一個 week_start。
create table if not exists public.availability_week (
  user_id    uuid     not null references public.profiles(id) on delete cascade,
  week_start date     not null,
  weekday    smallint not null check (weekday between 0 and 6),
  minute     smallint not null check (minute >= 0 and minute < 1440 and minute % 30 = 0),
  primary key (user_id, week_start, weekday, minute)
);

-- 「這個人動過這一週」。**沒有這張表就分不出「整週清空」與「沒填過例外」。**
create table if not exists public.availability_week_mark (
  user_id    uuid not null references public.profiles(id) on delete cascade,
  week_start date not null,
  primary key (user_id, week_start)
);
```

### `week_start` 是什麼

**那一週星期一的日期，以那個人自己的時區（`profiles.tz`）算出來的。**

理由：`availability.weekday` 與 `minute` 本來就是他自己時區的當地時間
（那一欄的註解明寫）。週的邊界必須用同一把尺，否則一個在休士頓的人與一個在台北的人，
「同一週」會指到不同的七天。

⚠ **`week_start` 存的是日期不是瞬間。** 它是一個曆法上的標籤，不是時間點。
前端算它的時候用既有的 `startOfWeek(date, tz, 1)` 再取當地日期，
不要自己寫日期運算（`availability/src/tz.js` 的檔頭寫著「不要重寫那三支」）。

### 為什麼不是在現有那張表加一欄日期

評估過，否決。那欄要允許空值（空 = 平常），而空值沒辦法乾淨地進主鍵；
更重要的是**既有每一段讀取都要改成「記得排除有日期的列」**，
漏掉任何一處的後果是某個人的例外被當成他平常的時間，**而且不會報錯**。
新增一張表的失敗方式是大聲的（查不到表），舊表的失敗方式是安靜的。

## 二、合併規則

看板現在的邏輯是：對每個成員的每一個固定格子，算出它在你這一週的哪些真實瞬間
（`slotInstants(weekStart, wd, min, ownerTz)`，回 0 到 1 個），再換算成畫面的格子。

改成兩層，而且**逐格判斷，不是逐人逐週判斷**：

1. 算出那一格的真實瞬間（跟現在一樣）。
2. 用那個瞬間反推**它落在成員自己時區的哪一週**（那一週的星期一）。
3. 那個 `(成員, 那一週)` 在 `availability_week_mark` 裡有紀錄，
   就只採用 `availability_week` 的格子；沒有就採用 `availability` 的固定格子。

### 為什麼一定要逐格

**你看的一週，對一個時差半天以上的成員來說可能橫跨他的兩個本地週。**
例如你在台北看 3/9 到 3/15 那一週，一個在休士頓的成員，他的「週日晚上」
落在你這一週的星期一凌晨 —— 那一格屬於他的**上一個**本地週。

如果用「這個成員這一週有沒有例外」一次判斷，跨週邊界的那幾格就會取錯那一邊，
而畫面上只會看起來像「這個人的時間怪怪的」。**這是這次最需要測試的一段。**

現有的 `slotInstants()` 已經處理了「落在觀看者這一週之外就回空陣列」，
所以第 1 步不用動；新的是第 2、3 步。

## 三、權限

照 `availability` 那張表既有的形狀，一條一條對齊：

- **讀**：`public.is_cadre()`。學員與沒登入的人一列都讀不到。
- **寫**：`auth.uid() = user_id and public.is_cadre()`，insert 與 delete 各一條。
- **`availability_week` 刻意不給 update 政策**，理由跟既有那張一樣：
  除了主鍵沒有別的欄位，「改時間」就是刪掉舊格子、插入新格子。
  沒有 update 政策也沒有 update 授權，等於「改到別人的列」這個 bug class 在這張表上不存在。
- **`availability_week_mark` 也不給 update 政策。** 它只有主鍵兩欄，沒有任何可以改的東西：
  設定一週就是 insert，取消就是 delete。**兩張新表都只有新增與刪除**，
  所以「改到別人的列」這個 bug class 在這個功能上完全不存在 —— 不是被政策擋住，是不存在。
  （初稿在這張表放了 `updated_at`，自我檢查時拿掉：沒有任何畫面用到它，
  而有那一欄就必須發 update 權限，等於為了一個沒人看的欄位打開一整類風險。）

⚠⚠ **一定要先 `revoke all ... from anon, authenticated` 再 grant。**
Supabase 在 public schema 設了 default privileges，**每一張新表自動把全部權限
發給 anon 與 authenticated**。既有的 `2026-09-02-availability.sql` 為了這件事當天就補過一份修補檔，
校友那批（`2026-09-18-alumni-stories.sql`）也踩過同一顆釘子。
少了那一句，下面那幾條逐欄授權全部變成裝飾。

### 存檔的寫法

照 `data.js` 既有的 `saveMine()`：**算出差集只寫差的那幾格**，不是先刪光再寫回。
先刪光再寫回的話，刪成功而插入失敗等於他那一週的資料沒了，而他以為只是存檔失敗。

⚠ **不准用 `.upsert()`。** 欄位層級授權的表用 upsert 會整句被資料庫拒絕，
症狀是「按了存檔沒反應」。這個 repo 2026-09-02 在 `availability_meta` 上踩過一次、
2026-09-11 校友那批又差點踩第二次。`scripts/check-upsert.mjs` 守著這件事，
`availability/src` 已經在它的掃描範圍內。

## 四、畫面

### 「我的時間」那一頁（`availability/src/ui.js` 的 `mineHTML()`）

上方多一個切換：**平常的時間** / **某一週**。

- 選「某一週」時，編輯的是**看板目前正在看的那一週**，頁面上用「上一週 / 下一週」移動，
  旁邊寫出那一週的日期範圍。

  **為什麼不做週次下拉選單**：Paul 要的是「本週加未來全部」，而下拉選單沒辦法無限長，
  設一個上限就等於偷偷把「全部」改成某個數字。看板本來就能往後翻不限，
  而 `S.weekStart` 已經是兩個分頁共用的狀態，所以「我在看哪一週就編哪一週」
  既沒有上限問題，也剛好是人想事情的順序。
- **本週之前的週不能編輯**：切到「某一週」時如果目前停在過去，那一頁顯示
  「過去的週不能改」並把「上一週」停用，不畫格子。
- 選了某一週之後，**預先帶出他平常的時段**當起點（若該週已有例外則帶出例外）。
- 底下一句話：「這一週會用這裡的設定，不會影響你平常的時間。」
- 已經設定過例外的週**列在這一頁**，每一個可以「回到平常的時間」（刪掉 mark 與那一週的格子）。
  沒有這一份清單的話，他會忘記自己設過，然後覺得看板跟他以為的不一樣。
- 存檔用同一顆按鈕、同一套訊息風格。**失敗一定要說話。**

### 看板（`availability/src/main.js`）

往後翻的四週上限拿掉，往前維持四週。現在那句「只能往後看四週」的訊息一併移除，
往前那句留著。

## 五、邊界情況

| 情況 | 行為 |
|---|---|
| 有例外、但一格都沒勾 | 那一週他完全沒空。看板那一週沒有他。**這正是要支援的情況。** |
| 沒有例外 | 用平常的固定時段（跟現在完全一樣）。 |
| 過去的週有例外 | 看板往前翻四週之內照樣顯示（歷史就是那樣），但**不能編輯**。 |
| 成員沒設時區 | 跟現在一樣：只跳過他自己，其他人照常顯示。 |
| DST 那兩天 | 沿用既有行為，不特殊處理（`tz.js` 檔頭寫明春季不存在的時刻會被收合、秋季重複的只回一個）。 |
| 例外資料放到過去 | **不自動清理。** 永遠不會被讀到（看板往前只翻四週），留著當紀錄比寫一支會刪資料的程式安全。 |

## 七、明確不做

- **不做單日例外。** 只有整週。做了單日就會有人要單一時段的例外，沒完。
- **不做重複規則**（每隔一週、每月第一週之類）。
- **看板上不標記誰是例外**（Paul 2026-09-12 拍板）。
- **不自動清理過去的例外。**
- **不改「平常的時間」那張表的任何行為。**
- **不碰 BT-Scheduler。** GOALS 明確寫著不合併、不給它加登入。
