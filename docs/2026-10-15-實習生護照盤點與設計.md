## 1. 盤點：現在這本護照是怎麼組的

### 1-1. 一句話

護照是「一個人、一本、33 格」。每格一個章，蓋章時可以寫一句心得、放一張照片。章是公開的（進度牆上大家看得到誰蓋了幾格），心得與照片只有本人看得到。

### 1-2. 前端長什麼樣

- `passport/index.html` 一頁加三支 js：`data.js` 唯一碰資料庫、`ui.js` 只畫畫面、`main.js` 只接點擊。
- 它讀 `shared/` 的三個共用檔：`supabase.js`（連線）、`auth.js`（登入與目前使用者）、`brand.css`（色票字體）。加上頂欄 `nav.js`。
- 活動文案不在程式碼裡，在資料庫。課程組要改題目，去 Supabase 的 Table Editor 改一格就生效，不用找工程師。
- 護照目前是**幹部專用**：頂欄的 `FEATURES` 清單把 `/passport/` 標成只給 `cadre` 看，而且資料庫那一側 RLS 也只放 `cadre`。前端藏連結只是順手，真正擋人的是資料庫。

### 1-3. 資料表（九張）

用白話講每張表是什麼。「RLS」（Row Level Security）是資料庫層的規則，決定「誰看得到、動得了哪幾列」，前端程式碼改不掉它。

| 表 | 是什麼 | 誰看得到 | 誰改得動 |
|---|---|---|---|
| `months` | 11 個月的順序與主題。學年制 9 月到隔年 7 月 | 幹部 | 後台改 |
| `activities` | 33 格的定義：編號（`09A` 這種）、月份、分類（聚會／題目／鏡頭）、中英標題、說明 | 幹部 | 後台改。**不能改編號**，章是靠編號對到格子的 |
| `passports` | 一人一本。現在只剩護照本身的欄位：一句話、核發日、引導頁看過沒 | 幹部 | 本人 |
| `profiles` | 這個人：中英文名、所屬 team、時區、大頭照、角色 `role`、後台職位 `board_role` | 自己，加上幹部看得到其他幹部 | 本人改名字 team 大頭照；`role` 跟 `board_role` 本人改不動 |
| `stamps` | 章。誰、哪一格、哪一天蓋的 | **幹部看得到所有人的**，進度牆靠這個 | 本人 |
| `entries` | 心得與照片 | **只有本人**，連「查得到但看不到內容」都不行 | 本人 |
| `destinations` | 24 個城市，入境章用的城市池 | 幹部 | 後台改。只能加不能刪，有人用過的城市資料庫會擋 |
| `visas` | 蓋滿一個月時發的入境章，記那個月抽到哪個城市，發了就不動 | 本人 | 本人只能新增與刪除，沒有「改」的權限，刻意的 |
| `milestones` | 蓋到第 N 個章解鎖的東西 | 幹部 | 後台改。**前端 2026-08-27 已移除**，表留著沒人讀 |

兩個設計重點，影響到實習生護照怎麼做：

- **章與心得分兩張表，不是一張。** 因為章要給進度牆看、心得不能給任何人看。合在一張表的話，進度牆為了讀章就必須讀得到那一列，心得就守不住了。
- **「誰達成了什麼」刻意沒有表。** 進度就是 `stamps` 數出來的，不另外存一份狀態，少一張要管 RLS 的表。

### 1-4. 角色怎麼守門

`profiles.role` 有三個值：`cadre`（幹部）、`student`（學員）、`alumni`（校友）。資料庫用 `check` 限制只能是這三個。

- **註冊後預設是 `student`**，什麼都沒有。
- 拿邀請碼呼叫 `claim_invite()` 才升級。升成什麼由那組碼的 `grants` 欄位決定（現在只有 `cadre` 與 `alumni` 兩種），不是前端說的。升成 `cadre` 的那一刻才會建 `passports` 那一列，所以**只有幹部有護照**。
- 護照八張表的每一條 RLS 都多了一句 `is_cadre()`：不是幹部連 `months`、`activities` 都讀不到。
- 後台另外有 `board_role`（`member` / `director` / `president`）管「誰能在 `/admin/` 核可、發碼」，跟 `role` 是兩件事。發邀請碼目前只有 Co-President 能做，而且 `create_invite()` 寫死只收 `cadre` 與 `alumni`。
- 頂欄的 `FEATURES` 只認 `role`，刻意不認 team。`nav.js` 檔頭明文禁止在那裡加 team 層級過濾。這一點對「只有 Internship team 看得到實習生護照」有影響，見方案。

### 1-5. 隱私界線

GOALS.md 寫「不動 `/passport/` 的隱私界線」，具體是：

- 公開給其他幹部的只有四樣：姓名、team、大頭照、蓋了哪幾格。
- 心得與照片只有本人。四種操作（讀、新增、改、刪）全綁 `auth.uid() = user_id`。
- 入境章的城市也只有本人，因為沒有任何畫面需要看別人的。
- 理由寫在 README 第 1 條：幹部裡有未成年人，外洩一次就再也沒有人會誠實寫。

### 1-6. 加一格、加一個里程碑要花多少

- **加一格活動**：在 Supabase 的 `activities` 表加一列，不用改程式。但護照的版面是「11 個月、每月 3 格」畫死的，加第 4 格會跑版，要改 `ui.js`。
- **加一個里程碑**：`milestones` 表加一列就好，但前端已經不讀這張表，等於沒有畫面。要用得先把功能做回來。
- **換一整套格子**（例如實習生用的）：`activities` 沒有「這是哪一套」的欄位，所有列都是同一本護照的。要分套就要加欄位，那是改表結構，照 GOALS.md 要先問你。

## 2. 設計提案：三個方案

先把三個方案的名字講清楚：

- **方案 A：同一本護照，加一套格子。** 在現有 `/passport/` 裡加「這套格子給誰」的概念，intern 進去看到的是另一套。
- **方案 B：另開一個資料夾 `/intern-passport/`，共用資料庫。** 複製護照前端成第二本，資料表共用但多一個「哪一本」的欄位。
- **方案 C：另開一個資料夾，而且另開一組表。** 完全獨立的第二本，只共用登入與 `shared/`。

### 2-1. 五個問題，三個方案各自怎麼答

**intern 是什麼角色**

三個方案都要先回答這一題，答案跟方案無關：

- 選項一：intern 就是 `cadre`，只是 team 填「Internship Team」。零改動。代價是 intern 會看到所有幹部功能（時間看板、申請管理、進度牆上所有幹部），而且會出現在幹部的進度牆上。如果 intern 是外面來的人，這樣等於把幹部內部的東西全開給他。
- 選項二：加第四個角色 `intern`。要改 `profiles.role` 的 `check`、`invite_codes.grants` 的 `check`、`claim_invite()`、`create_invite()`、`is_cadre()` 旁邊再加一支 `is_intern()`，以及護照所有 RLS。這是 GOALS.md 說要先問你的那種改動。
- **我的建議：加第四個角色。** 理由是「intern 不是幹部」這件事在組織上就是真的，而且以後 intern 期滿轉幹部或轉校友，用邀請碼升級的路本來就有。選項一省的是半天程式，付出的是把幹部內部的東西開給一群每學期換的人，而且永遠分不清進度牆上誰是幹部誰是 intern。
- 如果 intern 其實是學員（外面公司的實習），那就不該是新角色，應該是 `student` 加一個「我在實習」的狀態。這個情況下底下三個方案都要重想，請先回答第 0 節第 1 題。

**複用還是另開資料夾**

| | A 同一本加一套 | B 另開資料夾共用表 | C 另開資料夾另開表 |
|---|---|---|---|
| 符合「開一個資料夾、放一個 HTML、讀那三個共用檔」 | 不符合，是改現有功能 | 符合 | 符合 |
| 要改現有護照的程式 | 要。`data.js` 每個查詢多一個條件、`ui.js` 月份版面要能換 | 幾乎不用。但 RLS 要改成分得出哪一本 | 完全不用 |
| 要改表結構 | `activities`、`months`、`stamps`、`entries`、`visas`、`passports` 全部加「哪一本」欄位 | 同 A | 不改既有的表，新開一組 |
| 幹部護照會不會被弄壞 | 會有風險。所有查詢都在改 | 低。但 RLS 一改錯，intern 可能看到幹部的章 | 零。兩邊沒有交集 |
| 兩份幾乎一樣的程式碼 | 沒有 | 有。約 1,800 行前端複製一份 | 有，同 B |
| 以後幹部護照改了，實習生那本要不要跟 | 自動跟 | 要手動抄 | 要手動抄 |
| 換屆的人看得懂嗎 | 要懂「一套程式兩種行為」，難 | 「兩個資料夾兩本護照」一看就懂，但會問為什麼表是共用的 | 最直白：兩個資料夾、兩組表 |

**誰蓋章、誰看得到**

- 幹部護照是自己蓋，沒人核可。intern 的章如果也是自己蓋，三個方案都照抄。
- 如果要「帶的人蓋」或「帶的人核可」，那是新機制：`stamps` 要多一個「誰蓋的」或「核可狀態」，再加一條只有特定人能寫的 RLS。這在 C 最好做（新表想怎麼設計都不會影響幹部），在 A 最難（要在幹部不需要的表上加欄位）。
- 誰看得到進度：幹部護照是全體幹部互看。intern 的進度牆如果只給 Internship team 與 intern 自己看，三個方案都要寫一條新的 RLS，認「這個人在 Internship Team」。目前有 `is_director_of(team)` 可以借，但那是認 Director 不是認 team 成員，要再寫一支。

**心得隱私**

三個方案都照幹部那條線：心得與照片只有本人。不建議開「帶的人看得到心得」，理由跟幹部一樣，而且 intern 更可能有未成年人。如果 Internship team 需要看 intern 寫了什麼才能評估，那應該是另一個「交作業」的功能，不該混進護照的心得欄。

**邀請碼**

- 加第四個角色的話，`invite_codes.grants` 多一個 `intern` 值，後台發碼的下拉選單多一項。改動在 `create_invite()` 與 `claim_invite()` 各一行加一個 `check`。
- `claim_invite()` 現在的邏輯是「已經是幹部就不扣碼、不降級」。要補一條：幹部拿 intern 碼怎麼辦（建議同樣不動），intern 拿幹部碼算正常升級。
- 這一步要等 `create_invite()` / `disable_invite()` 在正式資料庫上找得到之後再做，不然是在還沒確認會動的東西上面疊。

### 2-2. 對 GOALS.md「明確不做」的檢查

- **不加框架、不加 build step**：三個方案都沒碰。
- **不做路由器、外掛系統，`shared/` 極小**：A 最接近踩線，因為「一套程式依使用者切換行為」就是路由器的雛形。B、C 不碰 `shared/`。
- **不動 `/passport/` 的隱私界線**：A 會動到那八張表的 RLS。B 會動 RLS 但不動界線。C 完全不碰。
- **不做管理後台（已被推翻，限定「承接申請與資源目錄」）**：如果要「帶的人蓋章」，那就是後台的新用途，不在推翻時定的範圍內，要你點頭。
- **不做站內通知中心、不做核可通知信**：intern 的章被核可也不寄信，照既有決定。
- **優先序規則**：intern 如果有未成年人，動到他們的資料就是第 1、2 級，「做得慢沒關係，做得漏不行」那一條適用。

### 2-3. 建議

**建議走方案 C（另開資料夾、另開一組表），角色加 `intern`。**

理由照 GOALS.md 的順序排：

1. **幹部護照零風險。** 現在有約 30 位幹部在用，優先序第 1、2 級是「不外洩、不弄壞」。C 是唯一一個不碰那八張表任何一條 RLS 的方案。
2. **最符合北極星。** 「開一個資料夾、放一個 HTML、讀那三個共用檔案」是 GOALS.md 說不能破壞的那句話，C 就是這句話的字面做法。換屆的人看到兩個資料夾兩組表，不需要理解「同一套程式為什麼有兩種行為」。
3. **格子可以不一樣。** intern 的一期是一學期不是一學年，格子是任務不是月份。硬塞進「11 個月乘 3 格」的版面會兩邊都不對。另開表，`intern_tasks` 想怎麼排就怎麼排。
4. **「帶的人蓋章」好加。** 如果第 0 節第 4 題的答案是「要」，新表加一欄一條 RLS 就好。

代價要說清楚：

- **會有第二份幾乎一樣的前端。** 約 1,800 行。幹部護照以後改了視覺，實習生那本要手動跟。緩解方式是第一版刻意做得比幹部護照簡單，不抄入境章、不抄 MRZ 機讀碼、不抄撕章動畫，只抄「格子、蓋章、心得、進度牆」四件事。抄得少，要跟的就少。
- **新開四到五張表、一支角色遷移檔。** `intern_passports`、`intern_tasks`、`intern_stamps`、`intern_entries`，加 `profiles.role` 與 `invite_codes.grants` 各多一個值。全部要先在本機跑過 `scripts/` 那套測試再上正式站，而且要排在既有那 8 支還沒跑的遷移檔之後。
- **Internship team 要自己維護任務清單。** 跟課程組改 `activities` 一樣，去 Supabase 改表。這是把「每學期改 JSON」換成「每學期改試算表」，照 GOALS.md 推翻「不做管理後台」時講的理由，後者比較交接得動。

**什麼情況我會改建議：**

- intern 其實就是幹部的一種、而且你不介意他們看到幹部內部功能：直接用 `cadre` 加 team，零程式，今天就能發碼。
- intern 是學員、護照記的是外面公司的實習：不是護照問題，是 `student` dashboard 的功能，應該放進目標 9 的 student 範圍重想。
- 格子跟幹部一樣是「月份乘三」、一期也是一學年：方案 B 划得來，省一份前端。
