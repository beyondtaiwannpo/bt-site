# 後台速度與自動儲存（2026-11-06）

Paul 2026-11-06 回報三件事：剛上線的側欄新項目重整之後不見了；後台換頁很慢；希望每一格都像 Workspaces 那一頁一樣「改了就存」，左下角那個通知留著。
這一份記的是量測、改法、改完的數字。做法與守門寫在 README「後台速度」「自動儲存」兩節。

## 一、先量再改（改前）

量法：Paul 本機的 Chrome（已登入、Co-President），正式站 beyondtaiwannpo.com，從台北連 Supabase（新加坡）。
每頁讀瀏覽器自己的 Performance API：`domInteractive` 是 HTML 解析完、`load` 是靜態檔全部到齊，「內容」是 `#bt-root` 裡「載入中…」那一句被真的畫面換掉的那一刻。
靜態檔都在 GitHub Pages 的 10 分鐘快取裡（跟幹部平常換頁一樣），所以數字量的是資料那一半。每頁量一次，不取平均。

### 看出來的事

1. **側欄跟頂欄要等全部資料回來才畫。** 每一頁的 `render()` 都在 `boot()` 最後面，前面每一趟 Supabase 都在「載入中…」後面排隊。總覽 3.6 秒裡，靜態檔 0.19 秒就到齊了，剩下 3.4 秒畫面上只有一句載入中。Paul 說的「很慢」就是這一段。
2. **「我是誰」每一頁重問一次，而且是兩趟串著問。** `loadMe()` 先讀 profiles，再 `await` my_access()，每頁固定先花 600 ms 才開始載真正的資料。換頁的時候這個答案十秒前才剛問過。
3. **總覽把六樣東西排隊載。** teams、todo、workspaces、requests、events、meetings 一個接一個 `await`，每個 300 ms。
4. **一趟熱的來回約 300 ms**（台北到新加坡），所以每少一層就少 0.3 秒。改法只有兩種：少一層、或並行。
5. 側欄項目「不見了」不是程式問題：GitHub Pages 把每個檔案快取 10 分鐘，四個資料夾各一份側欄，哪一份先過期哪一份先換新。改法是讓頁面自己發現「線上有更新的版本」。

## 三、改完再量

正式站還沒推上去（這一輪不 push），所以改前改後都在本機量，條件完全一樣：
`scripts/e2e/server.mjs` 那種靜態站，`shared/supabase-config.js` 指到一個**每一趟都延遲 300 毫秒**的代理，後面是本機 Docker 的 Supabase（跟正式站同一套結構、e2e 的種子帳號）。
改前是 `git archive HEAD`（aff9369）端出來的一份，改後是工作目錄。同一個分頁、同一個帳號（Co-President）、靜態檔在快取裡，每頁量一次。
代理對 CORS 的預檢（OPTIONS）也延遲，所以每一趟是 600 毫秒而不是 300，比正式站重；看比例不看絕對值。

「側欄」是真的側欄（不是骨架）畫出來的那一刻，「內容」是內容那一格的骨架被換掉的那一刻，「資料全到」是最後一趟 Supabase 回來。
「開頁就在」的意思是量測的程式在頁面 load 之後才注入，注入的時候已經在了（load 在 20 到 45 毫秒）。

改後的四個後台頁，第二次以後開（十分鐘內）都不再問 profiles 與 my_access，上表的「改後」就是這種情況；第一次開多一趟（兩個查詢同時發，600 毫秒）。

### 目標對照

- 外殼 100 毫秒內：四個後台頁的側欄骨架在 HTML 裡，load 在 20 到 45 毫秒就看得到；真的側欄在「我是誰」從快取回來那一刻（load 之後幾毫秒）。達標。
- 最慢那一頁內容快 40% 以上：總覽 5355 → 1899，快 65%。達標。
- 還沒做、要 Paul 決定的：/passport/ 本來就一層，沒動；/intern-passport/ 的進度牆（profiles 那一趟）還是等前面回來才發，再省一層要動 data.js 的結構，這一輪沒做。

## 五、要 Paul 看一眼的判斷

1. /settings/ 與 /passport/ 的 toast 本來就在畫面下方正中間（那兩頁沒有後台那套左下角 toast），這一輪沒有搬。要統一成左下角再說一聲。

4. 「我是誰」的分頁快取有一個邊角：帳號被停用、或資料庫整個重建（本機測試時遇到）的時候，十分鐘內那一頁的側欄還會畫出來，資料那一格變成「載不到」，不會像以前直接被送回登入頁。登出或關掉分頁就好。正式站不會自己重建資料庫，所以沒特別處理。
